## 重点话题

### 1. EIP-8130：从 owner 到有范围的 actor
**发生了什么**
- [EIP-8130：owner 改名为 actor，并定稿 Transaction Context 命名](https://github.com/ethereum/EIPs/pull/11764)（chunter-cb）提交并合并。理由是很多签名实体只是有范围的凭证（仅 PAYER、仅 SIGNATURE、会话式密钥），叫 owner 夸大了权限；`ownerId`、`OwnerConfig`、`authorizeOwner` 等相应改为 `actorId`、`actor_config`、`authorizeActor` 一类命名。
- [EIP-8130：`IAccountConfiguration.verify` 改名为 `verifyActor`](https://github.com/ethereum/EIPs/pull/11765) 提交并合并。
- [EIP-8130：加入 actor 调用策略和按 actor 的过期时间](https://github.com/ethereum/EIPs/pull/11766) 提交并合并。`actor_config` 中的 `policyType` 字节选择可选的调用策略，带签名的 `commitment` 和 `manager` 存在按 `(account, actorId)` 定位的策略槽中。策略在执行时检查而不是在验证时检查，协议判断交易有效性时不读取策略槽，因此策略不进入 mempool 的有效性判断面。

**为什么重要**
- 对钱包和 dapp：会话密钥、仅付费密钥这类受限权限有了统一名字和过期机制。策略只在执行期生效，节点验证交易的成本不会因策略变复杂而上升，这是原生 AA 设计中 mempool 安全与灵活性之间的取舍。

### 2. frame 交易的账户生态
**发生了什么**
- [ERC：frame 交易的模块化账户](https://github.com/ethereum/ERCs/pull/1794)（chiranjeev13）提交，[Magicians 讨论帖](https://ethereum-magicians.org/t/erc-8286-modular-accounts-for-frame-transactions/28695) 06:35，即 ERC-8286。它不改动 ERC-7579 的模块结构，只定义 EIP-8141 frame 交易的验证流程：验证器模块返回批准模式，账户在 VERIFY frame 中通过 APPROVE 指令执行它。
- [Magicians：EIP-8282 builder 执行请求](https://ethereum-magicians.org/t/eip-8282-builder-execution-requests/28699) 14:40（wemeetagain）。为 EIP-7732（ePBS）的 builder 在 EIP-7685 请求总线上提供独立的执行层请求合约，而不是借用验证者的存款和退出流程。

**为什么重要**
- 对智能账户团队：现有 ERC-7579 模块可以沿用到原生 AA，迁移成本更低。

### 4. ACDE #238
**发生了什么**
- 据 Ethereal news #26，ACDE #238（21:00）：glamsterdam-devnet-5 已上线（devnet-4 规范加 EIP-8045，被罚没验证者不能出块）；bal-devnet-7 是最后一个执行层专用 devnet；glamsterdam-devnet-6 目标约两周后，加入剩余执行层 EIP（EIP-7997 确定性工厂、EIP-8246 移除 SELFDESTRUCT 销毁）和初步重定价数值。Hegotá 非 headliner 提议包括数据重定价（EIP-8131 把 auth 数据计入 EIP-7623 下限、EIP-8279 BAL 字节下限）、EIP-7979 调用与返回操作码，以及 EOA 迁移到智能账户（EIP-7851 代码控制的 EOA 委托、EIP-8151 感知 ECDSA 授权停用的 ecRecover），会上还讨论了更广的 set code 方案。EIP-8222 lean staking 介绍了通过隐私池进行质押存款和提款。

**为什么重要**
- 对账户：EIP-7851 与 EIP-8151 解决 EIP-7702 之后的遗留问题，即 EOA 委托给代码后，原私钥能否被停用、ecRecover 如何感知。这决定 EOA 能否真正迁移成智能账户。
