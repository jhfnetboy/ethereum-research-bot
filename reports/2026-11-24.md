## 重点话题

### 1. 原生 AA 与 Frame 交易：EIP-8430 合并，EIP-8141 收紧签名数据读取
**发生了什么**
- [EIP-8430 AA Transaction Type 合并为草案](https://github.com/ethereum/EIPs/pull/12385) 2026-11-23 14:56（chunter-cb）。PR 描述列出的能力：分阶段的批量调用（调用可带原生 ETH）；gas 赞助，分绑定和开放两种付款方模式；2D nonce（key 0 就是账户 nonce）和免 nonce 模式；交易内置 EIP-7702 式代码委托（account_changes 类型 0x01）。认证器选择器、actor 解析钩子和预留的 account-change 类型，让其他账户模型不用新交易类型就能接入；EIP-8130（Keystore Accounts）在 PR #12386 里定义了其中一种接入。[讨论帖](https://ethereum-magicians.org/t/eip-8430-aa-transaction-type-split-out-from-8130/29810)。
- [PR #12708：EIP-8141 只允许 VERIFY 帧读取签名哈希之外的签名字节](https://github.com/ethereum/EIPs/pull/12708) 2026-11-23 21:00（soispoke）。对 msg 为空的 ARBITRARY 条目，签名哈希只覆盖其长度，转发交易的任何人都能改这些字节，而目前任何帧里的代码都能复制它们。改动后在 VERIFY 帧之外调用 SIGDATACOPY 读这类条目会直接停止，对签名哈希做的自定义见证检查必须放在 VERIFY 帧里。
- [PR #12506：EIP-8141 SENDER 模式下用默认代码设置代码](https://github.com/ethereum/EIPs/pull/12506) 2026-11-23 18:14 更新（AnkushinDaniil）。按 lightclient 的建议，SENDER 模式下的默认代码把 frame.data[0] 当选择器，0x01 表示 set code，对 tx.sender 执行 EIP-8298 的 SETCODEFROM，不加新标志，并把 EIP-8298 加入依赖。
- [PR #12672：EIP-8504 用依赖帧支持 leanSPHINCS 签名](https://github.com/ethereum/EIPs/pull/12672) 2026-11-23 23:03 更新（ilitteri）。依赖验证帧不执行代码，只声明 (scheme, data_hash, verification_key_hash) 三元组，目前只启用 leanSPHINCS；签名见证与交易分开携带，按 EIP-8288 的聚合接口处理，区块头承诺所携带的签名。
- [PR #12663（FOCIL 对 Frame 交易的遗漏见证）被关闭](https://github.com/ethereum/EIPs/pull/12663) 2026-11-24 01:37，未合并。
- [ACDT #104 会议总结](https://ethereum-magicians.org/t/all-core-devs-testing-acdt-104-november-23-2026/30411/3)：Frame 规范与 EIP-8288 的前向兼容引发讨论，焦点是用 proof frame 还是在签名列表里加入新方案来支持 LeanPCS 和 leanSPHINCS，涉及聚合、可延展性和 L2 集成；会议同意在 pq-el 和 8141 频道异步继续。（该总结为会议记录工具自动生成。）

**为什么重要**
- EIP-8430 给出了一条不必等 Keystore 账户、现有 EOA 就能用的原生 AA 路径：批量、赞助、并行 nonce 都进协议层，钱包不再需要 4337 的 bundler 和 EntryPoint 才能做这些事。它与 EIP-8141 Frame 交易是并行的两套设计，后续哪一个进入 Hegotá 仍未定。
- PR #12708 修补的是一类可延展性风险：签名哈希没覆盖的字节可以被中继改动，如果执行帧能读到它们，合约行为就可能被第三方影响。写 Frame 账户验证逻辑的开发者要把相关检查放进 VERIFY 帧。
- EIP-8504 和 ACDT 讨论表明，Frame 交易正在被当作后量子签名进入账户层的主通道，签名数据要能被区块级聚合。

**接下来关注**
- 下次 ACD 对 Frame 交易支持 leanSPHINCS 的方式（proof frame 还是签名列表）是否有结论，以及是否进入 Bogota Devnet 3。
- EIP-8430 与 EIP-8141 在 Hegotá 范围讨论里的取舍。

### 2. EIP-7702 授权新鲜度与 agent 账户的委托风险
**发生了什么**
- [EIP-8477 Recent Block Bound Delegation Authorizations 合并为草案](https://github.com/ethereum/EIPs/pull/12601) 2026-11-23 14:59（dangerousfood）。动机：未使用的 EIP-7702 授权在协议上没有有效期，只要账户 nonce 对得上就能随时被使用。方案扩展 type 0x04 的授权格式，要求签入执行层区块号和区块头哈希，只有该区块是包含区块前 256 个祖先之一时才能应用；保留 0x05 签名前缀，激活后拒绝旧的无锚定授权；授权列表的处理语义不变，也不会让已安装的委托失效。[讨论帖](https://ethereum-magicians.org/t/eip-8477-recent-block-bound-delegation-authorizations/30269)。
- [Policy-Enforced Agent Accounts 发布 Registry v2](https://ethereum-magicians.org/t/draft-erc-policy-enforced-agent-accounts/30467/10) 2026-11-24 03:21（palisec-dev）：按评审意见，发布者提交的每个策略都要经 setPending 并至少提前账户设定的 minDelay，只有账户自己能立即激活；注册表部署在 Robinhood Chain（4663），无 owner、不可升级，客户端库 0.2.0 已上 npm。此前 [palisec-dev 回复 Secrypta](https://ethereum-magicians.org/t/draft-erc-policy-enforced-agent-accounts/30467/7)（2026-11-23 14:39）同意在安全考虑里写明，策略承诺只覆盖需要策略签名者的操作，读者还要另外检查 allowance 和 permit、operator 授权、已安装模块和 executor、guard 和 hook、fallback handler，以及 ERC-7702 委托目标。[Secrypta 建议](https://ethereum-magicians.org/t/draft-erc-policy-enforced-agent-accounts/30467/8)（2026-11-23 16:39）把这些“出资面”快照做成独立的配套 ERC，因为快照只在拍摄的区块准确。
- [ERC-8516 Sovereign ERC-20 Receive Protection](https://ethereum-magicians.org/t/erc-8516-sovereign-erc-20-receive-protection/30485) 2026-11-23 22:55（radek）：ERC-20 的可选扩展，让 EOA 和智能账户都能对转入和铸造设门槛（白名单、黑名单、一次性链下签名或外部策略合约），针对地址投毒和垃圾转账。[ERCs PR #2213](https://github.com/ethereum/ERCs/pull/2213)。

**为什么重要**
- 7702 授权本质上是对“把账户代码换成某个合约”的签名。没有有效期意味着很久以前签过、没用掉的授权仍可能被提交。EIP-8477 把授权变成“短期有效”，对钱包的影响是：授权要在签名后约 256 个区块（按 12 秒出块约 51 分钟）内上链，离线预签、长期保存授权的做法将不再可行。
- Agent 账户的讨论落到同一点：真正能转走资金的往往是早先授予的权限和当前的 7702 委托目标，而不是策略本身。

**接下来关注**
- EIP-8477 是否被提议进入某个分叉；钱包和赞助交易服务如何处理授权过期后的重签。
- Policy-Enforced Agent Accounts 配套“出资面快照”ERC 的草案。

### 3. Gas 重新定价与后量子优先级：ACDT #104 和 PQAI #0
**发生了什么**
- [ACDT #104](https://ethereum-magicians.org/t/all-core-devs-testing-acdt-104-november-23-2026/30411) 2026-11-23 举行，议程第一项是 Glamsterdam 的 EIP-8037/EIP-8038 团队反馈。按[会议总结](https://ethereum-magicians.org/t/all-core-devs-testing-acdt-104-november-23-2026/30411/3)：Rahul（EF）汇总了各团队意见，Uniswap、Snowbridge、CoW Swap、Safe 等关注 try-catch 模式被打破和 gasleft 不变量，多数高中危问题预计在 1 月中旬前处理；Toni Wahrstätter 展示了 EIP-8037 可能的规范修改决策树，Maria Silva 解释去掉 reservoir 机制需要大幅提高交易上限并影响并行化；多数人倾向暂不改规范，最终决定在下次 ACD。Bogota Devnet 3 是否要做意见不一，推迟到下周。
- [EIP-8487 Separate execution credits and billing credits](https://github.com/ethereum/EIPs/pull/12637) 2026-11-23 14:59 更新（Giulio2002）：用同一个 tx.gasLimit 初始化两个计数器，credits 沿用旧的 gas 表，管 EVM 可见的执行额度；billing 用新表，决定手续费；billing 不足时整笔交易不可捕获地中止。这是让重新定价不打破合约 gas 假设的一种思路。
- [新草案 Bounded Storage Credit and Debit](https://github.com/ethereum/EIPs/pull/12707) 2026-11-23 19:18（cskiraly），作为停滞的 EIP-7519 的继任：SCREDIT 和 SDEBIT 在存储槽值处于上下界内时加减，按 SSTORE 计费，上界可服务 USDC 这类在余额字最高位放黑名单标志的布局。[讨论帖](https://ethereum-magicians.org/t/add-eip-bounded-storage-credit-and-debit/30477)。
- [EF 博客 PQAI #0](https://blog.ethereum.org/2026/11/23/pqai-0) 2026-11-23：EF 评估候选签名方案一年多后，主张用基于哈希的密码学替代椭圆曲线；三部分为共识（验证者用哈希签名）、用户账户（钱包提供迁到哈希签名的路径）、数据（blob 改用基于哈希的承诺）。文中写到 Justin Drake 在 Devcon 提出 2028 年 12 月的目标，EF 内部截止仍是 2029 年，1 月复审；Ethlabs 把自己的 Quick Slots 提案撤出 Hegotá 以腾出工程资源，EF 协议安全团队规模翻倍；剩余的 ACD 会议还会讨论从分叉中再拿掉哪些功能。[@ethereumfndn 转发](https://x.com/ethereumfndn/status/2125011648675029353)（2026-11-24 06:40）。

**为什么重要**
- EIP-8037/8038 已在测试网，会改变部分操作和状态的计费方式。依赖 gasleft 或 try-catch 留 gas 的合约（路由、跨链桥、多签）需要在主网激活前自查，ACDT 也建议多用 Forkcast 关注协议改动。
- PQAI #0 明确说“多年做的功能要等一等”，意味着 Hegotá 范围会向后量子收缩；钱包、多签和质押池都要准备签名迁移，签名变大还会影响节点硬件要求。

**接下来关注**
- 下次 ACD 对 EIP-8037 是否改规范的最终决定。
- 1 月的 PQ 时间表复审，以及哪些功能被移出 Hegotá。
