- [milonite 提出“同交易内创建再销毁”的退还问题](https://github.com/ethereum/pm/issues/2299#issuecomment-6917033995) 2026-11-16 19:56：EIP-8037 对同一交易内创建并自毁的合约仍收取 183,600 的账户创建 state gas，CREATE 从 32,000 涨到约 195,600（约 6 倍），用这种模式的整笔交易涨 1.6 到 2.8 倍。该模式用于临时充值地址等场景，主网约每天 2,100 个（2026-11-06），8 月约 1,200 个。原文的退还条款在 2026 年 5 月被 PR #11611 删除，恢复提案 PR #12249 被关闭；作者请求重新考虑，并指出 TCREATE（EIP-8360）不在 Glamsterdam 里，也不能直接替代已发出的地址。

**接下来关注**

### 2. EIP-8288 与 leanPCS：后量子签名和隐私证明的聚合路线
**发生了什么**
- [Vitalik 长帖：从认为 leanPCS 是胡扯到全力看好](https://x.com/VitalikButerin/status/2122233780371083553) 2026-11-16 14:42：
  - 8288 的核心是在 mempool 里聚合 STARK：用户发布 STARK、SPHINCS 签名或 PCS opening，各节点每个 tick 把新对象打包成一个包含“声明”列表的 STARK，只转发声明的哈希（每条约 64 到 96 字节）和一个证明，逐层聚合到区块里的一个总证明，链上只放声明本身，放进专门的 frame 类型。
  - 原因是量子安全后，签名从 65 字节（ECDSA）涨到 1 到 6 kB（WOTS/SPHINCS），ZK 证明从 200 到 1000 字节涨到约 128 kB（STARK），直接上链不可持续。
  - 三种选择：leanSPHINCS 只支持一种纯哈希签名，可让普通账户、多签以很少 gas（64 字节约 4096 gas）获得量子安全；leanSTARK 完全通用，可支持任意签名方案、隐藏内部逻辑的多签、隐私协议和“私密 AA”（一把钥匙控制多个账户而不公开关联），但需要协议规定 ISA，难以很快达成一致；leanPCS 只需规定一个域（自然选择是 128 位二进制域），在 EVM 看来相当于“PCS 神谕”，验证一个 STARK 约 2 万到 4 万 gas，通用性与 leanSTARK 相同且可能很快实现，ISA 确定后再加 leanSTARK。
- [soispoke：leanPCS 的 EIP 即将发布](https://x.com/soispoke/status/2122274148038672692) 2026-11-16 17:22，理由是不必先说服所有人内置一个新 ISA。
- [Toni Wahrstätter：EIP-8288 对隐私协议的意义](https://x.com/nero_eth/status/2122256845079203897) 2026-11-16 16:13：现在每笔隐私交易各带一个 ZK 证明、各自验证；有了 leanSTARK/leanPCS，可以在 mempool 聚合后一次批量验证，数据和计算都更少。
- [ethresear.ch：EIP-8288 的后量子签名聚合实测](https://ethresear.ch/t/exploring-post-quantum-signature-aggregation-for-eip-8288/26261) 2026-11-16 23:33，MultiVM Labs 的 manel1874 在 leanVM 下证明 Falcon-512、ML-DSA-44、FORS、Raccoon-128、Raccoon-G 五种签名的验证（Apple M4 Pro、24 GiB）。前四种能放进一个 leanSTARK；Raccoon-G 约 8.39 亿见证字超过 2.68 亿的上限，只能拆成 5 个证明再递归聚合。单签名测量中只有 Falcon-512 和 FORS 的峰值内存低于 4 GiB，因此更适合浏览器钱包。作者提出钱包本地签名、交给不受信任的外部聚合器出证明的流程，并指出 8288 草案里 LEANSTARK_SCHEME 仍为保留值、MAX_LEANSTARK_DEPS_PER_WRAPPER=1 需要调整。作者也在 [EIP-8288 讨论帖](https://ethereum-magicians.org/t/eip-8288-frame-type-for-pq-sig-and-stark-aggregation/28723) 23:42 引用了这组数据。
- [Frame 交易 Breakout #8](https://github.com/ethereum/pm/issues/2295) 今天 2026-11-17 21:00 召开，议程包括 L1 R&D 与 Devcon 小结、EIP-8288/leanPCS 的未来兼容性、devnet 状态和规范变化，并征集钱包、工具和应用开发者的反馈。

**为什么重要**
- 这决定了后量子账户的长期成本：签名不再逐笔上链和逐笔验证，钱包可以选择自己的签名方案（包括门限签名和硬件友好的方案），由网络统一验证聚合证明。
- 隐私方面，隐私协议的证明验证成本会被摊薄，这与 Vitalik 所说“执行密集型应用会更敢于加大用量”是同一个方向。

**接下来关注**
- soispoke 的 leanPCS EIP 草案，以及今晚 Breakout 对 8288 与 8141 兼容性的讨论结果。
- 钱包团队：测试中浏览器和手机的内存是瓶颈，自己出证明不现实，外部聚合器的服务形态值得提前评估。

### 3. Frame 交易账户：mempool 规则、权限分级和密钥恢复
**发生了什么**
- [EIP-8151 PR #12653 合并](https://github.com/ethereum/EIPs/pull/12653) 2026-11-16 17:09，新增公共 mempool 规则。EIP-8151 让 ecRecover 只对“无代码或 EIP-7702 委托”的账户返回结果，因此 EIP-8141 验证前缀里调用它会依赖第三方账户的代码。新规则：把每个被恢复的地址及其代码类别记为签名者依赖（tx.sender 除外），类别变化时重新验证；限制依赖同一恢复地址的待处理交易数，并按摘要分两档（针对本交易签名哈希 TXPARAM(0x08) 的恢复占保留份额，其他摘要占更小的份额，因为任何人都能拿到旧签名重放）；paymaster 的恢复每个 paymaster 只计一次。
- [EIP-8141 PR #12670](https://github.com/ethereum/EIPs/pull/12670) 2026-11-16 17:51 提交，在 8141 的策略摘要、直接评估和重新验证部分加上指向 8151 规则的条目。
- [EIP-8141 PR #12668](https://github.com/ethereum/EIPs/pull/12668) 2026-11-16 14:00 由 nerolation 提交：SPHINCS 账户把签名放进 ARBITRARY 条目（msg 为空），VERIFY frame 用 SIGDATACOPY 读取并按签名哈希和公钥校验后批准，不需要新的签名方案。
- [ethresear.ch：ERC-8403 账户即一个哈希](https://ethresear.ch/t/erc-8403-an-account-as-one-hash-and-post-quantum-keys/26147) 2026-11-17 00:53，johba 给出在运行 Nethermind EIP-8141 原型的 Daisugi 上、用哈希签名 Frame 账户的回执数据（签名在 EVM 里验证，未聚合）：
  - 无状态密钥（基于 keccak 的 leanSPHINCS 构造）转账 239,570 gas，VERIFY frame 59,909 gas，签名 5,684 B；协议 nonce 绑定的一次性 WOTS 密钥转账 101,984 gas，签名 1,417 B。无状态密钥时 VERIFY 之前的 frame 预留 75,100 gas，低于 10 万的 mempool 上限，但放不下两次这样的检查。
  - 实测发现：一个设备密钥试图撤销另一个设备时，交易因 VERIFY 有效而被打包，只有管理 frame 回滚。按 Slots16 现有设计，任何授权方都能替换整个授权集。
  - [AnkushinDaniil 回复](https://ethresear.ch/t/erc-8403-an-account-as-one-hash-and-post-quantum-keys/26147/4) 04:56：权限应写进叶子谓词，但必须在 VERIFY 里检查；建议在 slot 字中加一位，置位后拒绝任何指向账户自身的 sender frame，估计约多 2k gas。
- [ERC-8499 讨论](https://ethereum-magicians.org/t/erc-8499-hash-based-key-derivation-from-bip-39/30375) 2026-11-16 20:26 至 20:28，作者 johba 回应两点：签名计数是状态，助记词恢复不了，所以签名上限可能被用到的密钥类型，从助记词派生的密钥只用于给其他密钥做认证，每台设备用自己的密钥签名；恢复后找不到在用密钥时，钱包要说明尝试过哪些密钥类型、其他钱包可能找得到。
- [Magicians：多链同址 Safe 的检查范围](https://ethereum-magicians.org/t/checking-that-a-deployed-contract-still-runs-the-audited-commit/30318) 2026-11-17 00:58，Zealynx 补充：除签名者和门限外，已启用的 module 可以不经签名调用 execTransactionFromModule，1.3.0 起的 guard 可以否决所有者签名的交易，所以每条链都要读 getModulesPaginated 和 guard 槽位。

**为什么重要**
- EIP-8151 是 Vitalik 所说“ecrecover 变成有状态”的具体形态，mempool 规则补上了它和 Frame 交易同时上线时的 DoS 面。
- ERC-8403 的数据给出了后量子账户在没有聚合时的真实成本（一次无状态签名转账约 24 万 gas），也暴露了多设备账户的权限分级问题，这正是主题 2 里聚合方案要解决的成本背景。

**接下来关注**
- PR #12670 和 #12668 的评审；ERC-8403 是否采纳“管理位”方案。
- 运营多链多签的团队：监控项加上 module 和 guard，不要只看签名者和门限。
