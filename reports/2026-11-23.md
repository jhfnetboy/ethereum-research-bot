## 今日要点
1. 区块大小：[Nero 的 ethresear.ch 文章](https://ethresear.ch/t/whats-a-block-and-how-big-can-it-get/26281)（11-22 15:32）指出，按 Glamsterdam 定价，EL 区块在 266M gas 上限时可达到 EIP-7934 的 8 MiB；只上 EIP-8131 时，CL 的 10 MiB 消息上限在 339M 先被突破；两者都上之后，60M 时最坏信封约 1.02 MiB。

4. 账户与旧密钥：[EIP-8151 作者回应](https://ethereum-magicians.org/t/eip-8151-account-code-restricted-ecrecover/27690/30)（11-22 20:14）：可选预编译达不到目的，因为 ERC-20 permit、Permit2 等不可变合约写死调用 0x01，若 0x01 不变，退役的 ECDSA 密钥仍能通过它们转走资产。
5. 隐私与 AA：[kassandra 主张隐私协议走 4337 中继](https://x.com/kassandraETH/status/2124492676984619502)（11-22 20:18），认为通用的 UserOp 打包基础设施让使用隐私协议更无需许可，未来会过渡到 Frame 交易。

## 重点话题

### 1. 区块到底能有多大：gas 上限、字节上限与 FOCIL
**发生了什么**
- [Nero（Toni Wahrstätter）发表《What's a block, and how big can it get?》](https://ethresear.ch/t/whats-a-block-and-how-big-can-it-get/26281) 2026-11-22 15:32，全部数字以 Glamsterdam 规则、60M gas 上限为基准：
  - 两个字节上限测量的对象不同：EIP-7934 限制 RLP 编码的 EL 区块不超过 8 MiB；CL 限制每条 gossip 消息不超过 10 MiB。自 Gloas 起执行负载单独作为 SignedExecutionPayloadEnvelope 传播，信封约等于 EL 区块加 BAL 加执行请求，EL 侧检查看不到后两者。
  - 底价是 max 而不是相加：交易一旦按底价计费，只要固有 gas 加执行 gas 低于底价，额外执行就是免费的。零字节 calldata 每字节在底价是 64 gas、固有成本只有 4，留出 60 gas 的免费执行空间。
  - 最大的区块来自零字节 calldata 加被跳过的 EIP-7702 授权：chain ID 错误的授权在 ecrecover 前就被跳过，交易仍然有效，只付 EIP-2780 的 7,816 gas，而每个元组最多可达 133 字节。作者用 Amsterdam 执行规范构造出一个有效区块：4 笔交易，每笔 234,031 个零字节和 1,796 个授权，用掉 59.96M gas，大小 1,892,706 字节（1.805 MiB）。
  - 各方案下的临界点：仅 Glamsterdam 时，EL 区块在 266M 达到 8 MiB，信封在 330M 超过 10 MiB；加上 EIP-8131 后，EL 在 514M、信封在 339M（CL 先破）；EIP-8131 加 EIP-8279 后，EL 514M、信封 585M，60M 时最坏信封 1.02 MiB。作者特别指出只上 EIP-8131 不上 EIP-8279 会让两个上限之间的差距变得更糟。
  - 对 FOCIL 的影响：FOCIL 用 gas、nonce、余额判断 IL 交易“能否追加”，一旦字节上限可能起作用就不成立。chfast 的 execution-specs PR #4041 通过重新编码区块检查 RLP 大小来修补，但作者认为有四个问题：看不到 BAL 和请求字节；检查信封需要执行交易；SSZ 编码不归 EL 计算；被测量的区块并不真实存在。
  - 他的方案：EIP-8131 和 EIP-8279 一起上线（文中说明两者都已 CFI 进 Hegotá），EIP-8279 同时计量存款请求；加一个区块头检查 gas_limit <= MAX_GAS_LIMIT，按上述定价约 500M，若两者都没进 Hegotá 则取 256M；CL 用 C + ceil(k * bid.gas_limit / 64) 作为信封上限，k = 1.25 时 60M 下约 1.12 MiB 加 C，比 10 MiB 小约 9 倍。
- [PR #12686：EIP-8279 计量存款请求字节](https://github.com/ethereum/EIPs/pull/12686) 2026-11-22 13:50（nerolation）：Gloas 让 DepositRequests 成为无上限列表，每个请求给负载增加 192 字节，但 EIP-8131 和 EIP-8279 都不计量。中继合约循环调用存款合约，每笔约 26k gas，可以藏在零字节 calldata 的底价之下，把负载推到约 1.44 × gas_limit / 64（原本约 1.15×）。PR 规定存款合约发出带存款事件 topic 的 LOG 时计量 192 字节，与 EIP-6110 把日志转为请求的条件相同；正常存款的执行 gas（约 26k）远高于 12,288 的额外底价，不受影响。eth-bot 显示已获所有审阅者批准。
- [aelowsson 回复](https://ethresear.ch/t/whats-a-block-and-how-big-can-it-get/26281/2) 2026-11-23 00:57：EIP-7999 的思路是给每个 IL 分配区块数据上限的同等份额，用交易声明的数据上限来检查，这样数据上限独立约束信封，gas 上限可以继续提高；但数据资源同样要覆盖授权元组和请求，而声明数据上限需要新的交易格式。
- FOCIL 规范同步：[PR #12702](https://github.com/ethereum/EIPs/pull/12702) 2026-11-22 23:43（tcoratger）把 IL 的 MAX_BYTES_PER_INCLUSION_LIST 改为按 EIP-2718 编码计算（类型化交易是 type || payload，不是 RLP 项），与 Engine API 的 engine_getInclusionListV1 一致。[nero_eth 回复 chfast](https://x.com/nero_eth/status/2124445128353874120)（11-22 17:09）说还有更多问题，见 Discord 的 FOCIL 频道。

**为什么重要**
- 这直接关系到 gas 上限能提到多高。目前 60M 下这些情况都达不到，但 Nero 的测算说明，要往 200M 以上走，必须先把每个负载字节都按 gas 定价，否则字节上限会先成为瓶颈。
- 对账户最相关的一点：最坏区块来自 7702 授权元组在底价中不收费。EIP-8131 让授权按 133 字节计价后这条路就关闭了，批量授权和赞助交易的成本会小幅上升。
- 存款请求一旦计量，质押相关的中继合约在极端用法下会多付 gas，普通存款不受影响。

**接下来关注**
- EIP-8131 与 EIP-8279 能否在 Hegotá 一起上线，以及是否引入 MAX_GAS_LIMIT 区块头检查。[ACDE #250](https://ethereum-magicians.org/t/all-core-devs-execution-acde-250-december-3-2026/30463) 定于 12 月 3 日。
- PR #12686 合并时间，以及 FOCIL 频道提到的其余问题是否进入规范。

### 2. EIP-7702 与账户签名：规范修订、旧密钥风险和 PQ 迁移
**发生了什么**
- [PR #12685：EIP-7702 退款条件](https://github.com/ethereum/EIPs/pull/12685) 2026-11-22 12:41（tcoratger）：规范第 7 步说“authority 不为空”时退还 PER_EMPTY_ACCOUNT_COST - PER_AUTH_BASE_COST，而 Rationale 说“账户已存在于状态中”时退还。两者在“存在但为空”的账户上不同，参考实现按存在与否退款，PR 把第 7 步对齐到 Rationale。作者说明 EIP-7523 之后主网已没有这种账户，主网行为不变。
- [PR #12689：EIP-7702 签名载荷](https://github.com/ethereum/EIPs/pull/12689) 2026-11-22 21:04（tcoratger）：规范写签名是对 keccak256(SET_CODE_TX_TYPE || TransactionPayload) 签的，而 TransactionPayload 末尾包含 signature_y_parity、r、s，字面上签名覆盖了自己。PR 改为像 EIP-1559、EIP-2930、EIP-4844 那样逐项列出不含签名的字段。两个 PR 都需要 7702 作者（adietrichs、lightclient、samwilsn、vbuterin）之一和一位编辑审核。
- [EIP-8151 作者回应](https://ethereum-magicians.org/t/eip-8151-account-code-restricted-ecrecover/27690/30) 2026-11-22 20:14（colinlyguo）：EIP-8151 让 ecRecover 遵循 EIP-3607 的账户代码限制（EIP-7702 委托指示符除外），并与 EIP-7851 的 0xef0101 停用授权对齐。对“做成可选预编译”的建议，作者说主要目标是 ERC-20 permit、Permit2 这类写死调用 0x01 的不可变合约；0x01 不变，退役的 ECDSA 密钥仍能通过这些合约转走资产。
- PQ 迁移讨论：[Vitalik 回复](https://x.com/VitalikButerin/status/2124487160736973184) 2026-11-22 19:56：几乎所有非哈希签名方案在构造中也用到哈希，所以“只依赖曲线或格”不存在，选择只有“只依赖哈希”或“同时依赖哈希和别的东西”。[gballet](https://x.com/gballet/status/2124623820497555591) 11-23 04:59 认为，弄清楚如何升级以太坊的签名方案比决定具体方案更紧迫。[decentrek](https://x.com/decentrek/status/2124603905833324867) 11-23 03:40 回答提问时说，EIP-8130 本身可以支持 PQ 签名，但 Base 还没说会支持 leanSPHINCS 还是其他方案（或都支持）。

**为什么重要**
- EIP-7702 已经上线，两处修订都是让规范文字与参考实现一致，主网行为不变，但对新客户端和审计者有意义：按字面实现可能算错退款或签名哈希。
- EIP-8151 说明了一个账户迁移的现实问题：EOA 换成新签名方案后，旧 ECDSA 密钥仍可通过 permit 类合约授权转账。迁移方案必须在协议层处理 0x01，钱包也要提醒用户撤销旧密钥上的 permit 和授权。
- Vitalik 的回复把 PQ 签名的选择收窄为“纯哈希”与“哈希加其他假设”，与上期 Dankrad 提的“PQ 签名加 EC 签名”双签名思路一致。

**接下来关注**
- PR #12685 和 #12689 的作者审核；EIP-8151 是否进入某次升级的讨论。
- [PQ-CL Breakout #4](https://ethereum-magicians.org/t/pq-cl-breakout-4-november-24-2026/30460) 定于 11 月 24 日。

### 3. 隐私与账户抽象：4337 中继路径、Frame 交易隐私池和 Agent 账户安全
**发生了什么**
- [kassandra 谈 4337 隐私中继](https://x.com/kassandraETH/status/2124492676984619502) 2026-11-22 20:18：隐私协议的提款和交易走 4337 中继路径意味着自由和选择，4337 打包是通用基础设施，很多服务都在打包 UserOp。[她 20:33 补充](https://x.com/kassandraETH/status/2124496532896678166)：不想依赖协议专用中继的可用性、规则或费用，账户抽象就是出路，今天是 4337 打包，明天是 Frame 交易。
- 与 anondotinc 的讨论中，[kassandra 22:27](https://x.com/kassandraETH/status/2124525150917820748) 认为 4337 中继路径配合 paymaster 可以获得较强隐私；[23:38](https://x.com/kassandraETH/status/2124543144742011223) 指出若不愿泄露“同一用户在移动 WETH（手续费）和其他资产”，可以用 ZK 证明手续费 UTXO，可行但增加 gas；[11-23 00:02](https://x.com/kassandraETH/status/2124549166827246062) 补充 Railgun 的 unshield 总带有承诺的代币标记属性。
- [Frame 交易隐私池讨论新回复](https://ethresear.ch/t/a-privacy-pool-on-frame-transactions-what-works-and-the-case-that-does-not-yet/26223/5) 2026-11-22 19:27：原帖（11-06，Nethermind）在 Frame 交易上跑了 BN254 Groth16 隐私池，提款 679,322 gas、无需中继，但证明检查超过验证 gas 上限，池子也无法代表用户自己的地址发起调用。liamwilliams 认为 EOA 场景对身份绑定的操作是真实需求（领空投、投票委托、续费域名），但频率低且集中在领取事件，建议当作兼容性功能，先测量领取和投票流程再决定是否为此提高验证预算。
- Agent 账户安全评审继续：[Secrypta 对 Policy-Enforced Agent Accounts 的评审](https://ethereum-magicians.org/t/draft-erc-policy-enforced-agent-accounts/30467/4)（11-22 17:32）指出，多数资金被盗并不改策略，而是走早先授予且未撤销的权限：ERC-20 allowance 或 permit、operator 授权、已安装的模块或 executor，对 7702 账户则是委托目标本身；建议证据层暴露 7579 executor 和当前 7702 委托目标。[Zealynx 核查参考注册表](https://ethereum-magicians.org/t/draft-erc-policy-enforced-agent-accounts/30467/5)（11-23 04:53）后确认 declare 在同一区块生效，签名者更换等于把策略放宽到任意，建议 declare 也要遵守最小延迟。
- [ERC-8507 Agent Allowlist Framework 发布 0.2.0](https://ethereum-magicians.org/t/erc-8507-agent-allowlist-framework-aaf/30456/4) 2026-11-23 00:46：草案拿到编号并更名，按评审意见加入按动作声明的复用策略（NONE、WHILE_CURRENT、ADMISSION，默认 NONE）。此前 [Secrypta](https://ethereum-magicians.org/t/erc-8507-agent-allowlist-framework-aaf/30456/2)（11-22 17:31）提醒：EIP-7702 账户可以随时重新委托，地址不变代码变，白名单条目应可选择锁定评估时的委托目标或代码哈希。

**为什么重要**
- 隐私协议提款需要有人付 gas。走通用的 4337 打包或未来的 Frame 交易，用户不再依赖协议自营中继，这是“隐私 + AA”最直接的落地方式；手续费输出如何不泄露关联，是接下来实现上要解决的点。
- Agent 账户的评审反复指向同一点：7702 委托目标和已授予的权限才是真正的资金出口，只看策略承诺不够。

**接下来关注**
- Frame 交易验证 gas 上限是否为隐私池提高（上期讨论的 MAX_VERIFY_GAS）。
- 用 7702 或模块化账户跑 agent 的开发者：定期审计 allowance、permit 和已安装模块，并记录当前委托目标。
