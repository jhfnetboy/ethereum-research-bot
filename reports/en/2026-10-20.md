## Key topics

### 1. Retiring an EOA's key with SETCODEFROM
**What happened**
- [Magicians: Pre-ERC, an adoption profile and reference kernel for EOAs adopting code via SETCODEFROM](https://ethereum-magicians.org/t/pre-erc-adoption-profile-and-reference-kernel-for-eoas-adopting-code-via-setcodefrom/30020), 18:02 (nezu511), with 27 posts and 30 likes that day. EIP-8298 lets an EOA adopt account code at its own address, and EIP-8151 makes ecrecover stop returning addresses that hold regular code. Combined, the secp256k1 key can no longer send transactions or pass ecrecover for that account, and no assets need to move. Adoption is one-way, with no return to empty code, so the adopted code and the adopting transaction must be right the first time. The author found seven failure modes, most irreversible; for example, code that falls back to `ecrecover(...) == address(this)` locks the account out the moment it is adopted. On chains with an inclusion path that skips the sender-code check, such as OP Stack deposits, this only holds once the account has migrated where that path originates.

**Why it matters**
- This is a post-quantum route that complements bunker mode: instead of moving to a new address, the address itself switches to code control. For wallet developers, the adopted code must be audited and proven on testnets first, which is what the reference kernel and adoption profile are for. For users, this is irreversible, so wait until wallets offer an audited path.

### 2. Wallets and transactions: ERC-7902 and EIP-7906
**What happened**
- [ERC-7902 PR: wallet capabilities for EIP-8141 frame transactions](https://github.com/ethereum/ERCs/pull/2091) was merged (forshtat). The rationale is that AA progress has shifted fully to frame transactions, while among existing capabilities only `eip7702Auth` has seen meaningful adoption. After the update, a dApp can request frame transaction features through `wallet_sendCalls`, including the Hegotá candidates keyed nonces, recent roots and transaction assertions.
- [EIP-7906: remove TXDIFF](https://github.com/ethereum/EIPs/pull/12530) was merged, as was [including tx.sender in nonces_changed only when its account nonce changes](https://github.com/ethereum/EIPs/pull/12554).
- [Derek Chiang: a visualization of EIP-8288, recursive mempool aggregation](https://x.com/decentrek/status/2112535053188145367), 20:23, a system whose scalability increases with decentralization.
- [New EIP: eth/73 recursive STARK exchange](https://github.com/ethereum/EIPs/pull/12551) (nerolation).

**Why it matters**
- ERC-7902 is the interface between dApps and wallets. Its move to frame transactions shows wallets are also preparing for native AA in Hegotá; dApp developers will be able to request batching, sponsorship, assertions and more through the same `wallet_sendCalls`.

### 3. Privacy Pools v2 goes live
**What happened**
- [0xbow: Privacy Pools v2 is live](https://0xbow.io/blog/privacy-pools-v2-is-live) (blog dated October 20) on Ethereum mainnet, Arbitrum, Base, OP Mainnet, BNB Chain, Robinhood Chain and Citrea. v1 only allowed depositing and later withdrawing to a new address; v2 lets funds move inside a shielded pool. Transfers in the pool reveal neither sender, recipient nor amount, and v2 adds payment request links, swaps routed through LI.FI and yield through Aave v3 (notes hold ERC-4626 shares). A balance is a set of notes; only a Poseidon commitment goes onchain, and spending publishes a nullifier. Every deposit carries a private label, screened by the Association Set Provider (ASP) run by 0xbow, which publishes the approved label set onchain; a declined deposit can always ragequit through a public exit. Privacy keys are derived from a wallet signature and registered in an onchain keystore, so the spending key can be rotated without moving funds, and a relayer pays gas and takes its fee in the asset being moved.

**Why it matters**
- Compliant privacy is moving from simple mixing to an embeddable privacy layer: it works with any EVM address and needs no new seed phrase, and it is part of the EF's Kohaku initiative, with Ambire among the first adopters. Wallets and payment apps can integrate through the Privacy Pools SDK, with a Rust SDK planned for Q4 and multisig and hardware wallet support in development. Users can try it at privacypools.com, and v1 funds remain available at v1.privacypools.com.
