## Key topics

### 1. The Binance incident and the security boundary of EIP-7702
**What happened**
- [Ethereal news #45](https://ethereal.news/ethereal-news-weekly-45/): Binance had a $6.3B security incident, says it will cover losses, and about $3B has been frozen so far.
- [tayvano: the prior biggest hack was Bybit at about $1.5B; in the hours after this one, twice that amount was frozen, and more still was not](https://x.com/tayvano_/status/2116032165368709234), 11:59.
- [Martin Köppelmann: seeing rumors blaming EIP-7702 for the Binance hack](https://x.com/koeppelmann/status/2115927796992393407), 05:04; from what he can see, 7702 was just used to perform the hack efficiently and was not the root cause.
- [Derek Chiang: quick notes on 7702](https://x.com/decentrek/status/2115960332032299192), 07:13; 7702 itself is not broken, and there is no need to panic if you use a wallet that supports it (MetaMask, Uniswap, Ambire and others).
- [New EIP: permanent EOA delegation opt-out](https://github.com/ethereum/EIPs/pull/12600) (nicolashw, [EIP-8476 discussion thread](https://ethereum-magicians.org/t/eip-8476-permanent-eoa-delegation-opt-out/30134), 23:35). An EOA installs a non-executable code marker through a previously invalid type-4 self-transaction with an empty authorization list, after which no authorization, including a clearing one, can replace it. The EVM treats the marker as empty code (`EXTCODESIZE` is 0), so the account remains an ordinary EOA to contracts. The motivation is that institutional wallets, exchange hot wallets and treasuries do not need delegated execution and their operational controls may assume it is unavailable; it does not protect against private key compromise.
- [New EIP: recent block bound delegation authorizations](https://github.com/ethereum/EIPs/pull/12601) (dangerousfood, EIP-8477). Unused 7702 authorizations currently have no protocol-enforced freshness bound and stay usable whenever the nonce matches. The proposal has each authorization sign an execution block number and header hash and apply only while that block is one of the inclusion block's preceding 256 ancestors; legacy unanchored authorizations are rejected after activation, and installed delegations are unaffected.

**Why it matters**
- 7702 gives an EOA contract powers with a single signature, which also means efficiency for an attacker. For institutions and exchanges, EIP-8476 offers a protocol-level way to never use 7702; for wallets, EIP-8477 would make signed but unused authorizations expire on their own. Both are drafts, so for now the defense is still to never sign unclear authorizations and to check delegation targets.

### 2. Frame transactions and account specs
**What happened**
- [EIP-8141: clarify EXTCODEHASH restrictions for precompiles](https://github.com/ethereum/EIPs/pull/12596) (yperbasis). Under EIP-1052, an empty precompile account returns 0 from `EXTCODEHASH`, and sending it 1 wei changes the result to `keccak256("")`, so one transfer can invalidate many pending frame transactions; the draft bans `EXTCODEHASH` of active precompiles during validation.
- [EIP-8288: reuse proofs before recursive aggregation](https://github.com/ethereum/EIPs/pull/12595) (Marchhill).
- [ethresear.ch: post-quantum signatureless authorization with recursive verification](https://ethresear.ch/t/post-quantum-signatureless-authorization-with-recursive-verification/26196), 14:13; an authority publishes a commitment to a reusable secret, and each action is authorized by a fresh proof of knowledge.
- [New ERC: ERC-20 delayed unlock](https://github.com/ethereum/ERCs/pull/2129) and [ERC-20 outgoing window limits](https://github.com/ethereum/ERCs/pull/2130) (shargon), with opt-in holder-controlled outgoing locks, block-based unlock delays and an independent guardian veto.

**Why it matters**
- Validating frame transactions in the public mempool cannot depend on state any third party can cheaply change, or it becomes a low-cost DoS. ERC-20 outgoing limits add a delay at the token level for theft scenarios.
