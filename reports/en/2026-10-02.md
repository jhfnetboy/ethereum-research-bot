## Highlights
1. **zkAPI**: deposit credits into an Ethereum vault once, then authorize bounded usage with zero-knowledge proofs. The API provider sees the requests and the payment layer sees the spend, but neither can link them to an identity.
2. **EIP-8288 private transfers**: soispoke showed private, post-quantum transfers under EIP-8288.
3. **Stealth addresses as a minimal standard**: Kassandra suggests everyone first agree on one simple standard for receiving privately, and let each wallet decide how to manage privacy from there.
4. **Spec refinements**: several clarifications to Glamsterdam's EIP-7928 BAL were merged, and EIP-8298, a Hegotá candidate, now records adopted code as a hash in the BAL.

## Key topics

### 1. Private payments: zkAPI and EIP-8288
**What happened**
- [EF Blog: zkAPI, private usage credits for any API](https://blog.ethereum.org/en/2026/10/01/introducing-zkapi), announced by the EF on X at 03:14 ([@ethereumfndn post](https://x.com/ethereumfndn/status/2105753290977980682)). You deposit credits into an Ethereum vault once, then authorize bounded usage with zero-knowledge proofs instead of an identity. The example given is private AI inference.
- [soispoke: private, post-quantum secure transfers under EIP-8288](https://x.com/soispoke/status/2106055901446549680), 23:17.
- [Kassandra: stealth addresses should be a minimal standard all wallets can adopt](https://x.com/kassandraETH/status/2106056728353620188), 23:20. The shared part is receiving privately; the rest of privacy management is left to each wallet.

**Why it matters**
- zkAPI separates pay-per-use from identity. For users, it means buying API credits without an account; for developers, it is a ready pattern for anonymous billing on Ethereum. If stealth addresses converge on a minimal common standard, the cost for wallets to support private receiving drops sharply.

### 2. Refining BAL (Glamsterdam) and SETCODEFROM (Hegotá candidate)
**What happened**
- [EIP-8298: record adopted code as a hash in the BAL and reject same-transaction-created sources](https://github.com/ethereum/EIPs/pull/12399) was merged (CPerezz).
- Three EIP-7928 (block-level access lists) clarifications were merged: [storage key ordering](https://github.com/ethereum/EIPs/pull/12415) (nerolation), [empty BAL conditions](https://github.com/ethereum/EIPs/pull/12416) and [the access cost of a warm `SELFDESTRUCT` beneficiary](https://github.com/ethereum/EIPs/pull/12408) (colinlyguo).
- [EIP-8159 aligned with EIP-7928 BAL storage types](https://github.com/ethereum/EIPs/pull/12397) was merged.

**Why it matters**
- SETCODEFROM lets an account reuse existing code, so like 7702 delegation it directly affects where account code comes from. Recording a hash in the BAL keeps the code source unambiguous during parallel validation. BAL is already heading to testnets with Glamsterdam, so contract and wallet developers should start testing against the spec. SETCODEFROM is still a Hegotá draft and open for discussion.
