## Key topics

### 1. EIP-8141 mempool and paymaster
**What happened**
- [EIP-8141: define replacement, eviction and payer exposure for the public mempool](https://github.com/ethereum/EIPs/pull/12007) (svlachakis), submitted. Replacement: pending identity is `(sender, nonce)`, and signature- or witness-refreshed variants are replacement candidates, which closes signature-malleability churn; replacements must be independently valid, bump both fee fields by a node-configured minimum, and may switch payer, with reservations moving atomically. Payer exposure: the canonical paymaster's reservation accounting generalizes to every payer, so summed pending maximum costs never exceed the payer's balance, preventing one balance change from invalidating many pending transactions at once.
- [EIP-8141: define the transaction log set and unrolled-batch log semantics](https://github.com/ethereum/EIPs/pull/12008) (svlachakis), submitted: the transaction's logs are the frame receipts' logs in frame order, and an unrolled frame's logs are discarded with its state changes; otherwise two clients could agree on the receipt encoding and still disagree on the header `logsBloom`.
- [EIP-8141: specify the canonical paymaster implementation](https://github.com/ethereum/EIPs/pull/12012) (svlachakis), submitted, replacing the placeholder with a normative storage layout, payment authorization, treasury rules, admin interface and per-fork code hash recognition.
- AnkushinDaniil submitted two RFCs: [recognize the canonical paymaster by stable identity rather than exact bytecode match](https://github.com/ethereum/EIPs/pull/12010), meaning an EIP-7702 delegation to a reserved address or a code hash pinned per fork, and [formalize the signature scheme table as an in-protocol registry](https://github.com/ethereum/EIPs/pull/12011), where a signature scheme is a cryptographic operation the protocol supports in optimized form, not an account.
- Merged: [blob support for frame transactions](https://github.com/ethereum/EIPs/pull/11985), [direct evaluation of protocol-defined validation prefixes](https://github.com/ethereum/EIPs/pull/12001), [the APPROVE opcode gas cost](https://github.com/ethereum/EIPs/pull/12003), and [static bounds on fee fields](https://github.com/ethereum/EIPs/pull/12005).

**Why it matters**
- For paymasters: the payer exposure bound ties how many transactions a sponsor can have pending to its balance, and once the canonical paymaster implementation is settled, wallets can use a protocol-recognized sponsorship path without deploying their own contract. For wallets: the replacement rules define how to build "speed up" and "cancel" transactions.
