## Key topics

### 1. Sponsorship and revert semantics in EIP-8141 frame transactions
**What happened**
- [EIP-8141: allow EOA sponsor again](https://github.com/ethereum/EIPs/pull/11954) (lightclient), submitted and merged. #11814 restricted the signature in the default code to index 0 as a simplification, which broke the ability of codeless EOAs to sponsor; now the expected signature index depends on the frame scope: index 0 for execution and pay-plus-execution, index 1 for pay only.
- [EIP-8141: use skipped receipt status code](https://github.com/ethereum/EIPs/pull/11953) (lightclient), submitted and merged, changing the status code from 0x3 to the next available value, 0x2.
- [EIP-8141: approval effects are not reverted by frame revert or atomic-batch unroll](https://github.com/ethereum/EIPs/pull/11955) (AnkushinDaniil), submitted. `APPROVE(APPROVE_PAYMENT)` increments the nonce, sets `payer` and collects the maximum cost, but the spec did not say whether these roll back when an atomic batch fails: one client rolling `payer` back to none would make the transaction invalid while another treating it as transaction-scoped would keep it valid, so they would disagree on the same block. The PR states these effects are transaction-scoped.
- The same author also submitted [a note on sponsor repayment reversibility, batching the repayment in Example 3](https://github.com/ethereum/EIPs/pull/11956): in the example the sponsor approves payment in frame 1, while the ERC-20 repayment (frame 2) and the sponsee's call (frame 3) are separate; a non-batched frame that reverts discards only itself, so the sponsor could pay without being repaid.

**Why it matters**
- For paymasters and wallets: EOAs sponsoring directly means paying gas for others without deploying a contract, and transaction-scoped approval effects mean the fee is collected once payment is approved, so sponsors should put the repayment and the user's call in one atomic batch to protect themselves.

### 2. Charging and mempool in EIP-8250 and EIP-8272
**What happened**
- [EIP-8250: price nonce_keys and nonce_seq as transaction data](https://github.com/ethereum/EIPs/pull/11958), submitted; up to 16 32-byte keys, about 512 bytes, were previously free. [Exclude KEYED_NONCE_FIRST_USE_GAS from MAX_VERIFY_GAS accounting](https://github.com/ethereum/EIPs/pull/11957), submitted, pointing out that the 20000 gas first-use surcharge collides with the mempool validation gas cap.
- [EIP-8272: restore the signatures field in the payload and elide signature bytes in compute_sig_hash](https://github.com/ethereum/EIPs/pull/11959), submitted, since otherwise clients could disagree on the signature hash; [strengthen public-mempool handling of recent root references](https://github.com/ethereum/EIPs/pull/11961), submitted, recommending that expired references SHOULD be evicted, that near-expiry ones not be admitted, and that the number of pending transactions sharing a reference be bounded; all are node policy, not consensus changes.

**Why it matters**
- For gas and the mempool: these are DoS surfaces, either under-charging or batch invalidation, that implementers are closing before devnets.
