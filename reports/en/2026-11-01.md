## Key topics

### 1. The security boundary of EIP-7702 delegation: permanent opt-out and permit compatibility
**What happened**
- [EIPs PR #12605: EIP-8151 treats the 0xef0200 opt-out marker as a qualifying EOA](https://github.com/ethereum/EIPs/pull/12605), opened at 16:01. EIP-8151 (Account Code Restricted ecRecover) currently lets only accounts with empty code or a `0xef0100 || delegate` designator use `ecrecover`. If it shipped alongside EIP-8476, permits signed by accounts that opted out of 7702 would return an empty result, which contradicts the intent of removing only the delegation ability while keeping normal EOA behavior. The PR simply adds the EIP-8476 marker to the qualifying set.
- Background: [EIPs PR #12600: Add EIP-8476 Permanent EOA Delegation Opt-Out](https://github.com/ethereum/EIPs/pull/12600) (opened 2026-10-30). Once the account code is set to the exact marker, every future authorization, including one that clears delegation, is rejected. The EVM treats the marker as empty code (`EXTCODESIZE` is 0 and `EXTCODEHASH` is the empty code hash).
- [Ethlabs week 19 update](https://ethlabs.org/updates/week-19.html), published at 18:33, quotes Derek Chiang's note from 10-30: 7702 itself was not compromised, and people using 7702-capable wallets (MetaMask, Uniswap, Ambire and others) do not need to panic. Barnabé expects more onchain rate limits and circuit breakers run by agents on top of the new account capabilities.

**Why it matters**
- The Binance incident made the risk that "a delegated EOA can be drained" far more visible. EIP-8476 gives users who do not want AA a way to close the door for good, and the EIP-8151 revision makes sure that permits, sign-in with Ethereum and other `ecrecover` flows keep working afterwards. Wallets and dapps that check whether an address is a plain EOA will need to recognize the `0xef0200` marker too.

**What to watch**
- Whether EIP-8476 and EIP-8151 enter Hegotá discussions, and whether wallets add a one-click way to opt out of 7702 permanently.

### 2. EIP-8141 Frame Transaction: nonce boundary fix
**What happened**
- [EIPs PR #12603: Update EIP-8141 Transaction nonce check boundary](https://github.com/ethereum/EIPs/pull/12603), merged at 18:20. The spec now accepts a sender nonce of at most `MAX-1`, matching the frame transaction implementation for the bogota fork in execution-specs. The PR is labeled Bugfix, Breaking Change and Action Required for implementers.

**Why it matters**
- EIP-8141 is the main native account abstraction proposal: a transaction is split into verification frames and execution frames, and the account defines its own validation logic. Edge cases like this decide whether clients agree with each other, so the earlier they are fixed the better.

**What to watch**
- Whether client teams ship the same fix, and when the next Frame Transaction breakout call is scheduled.

**What happened**

It says AI progress is compressing estimates of the quantum threat timeline, and that experts met in Cambridge to coordinate the upgrade to quantum-resistant cryptography. See the [Cambridge post-quantum workshop page](https://pq.ethereum.org/cambridge/).
- [EIPs PR #12604: Add EIP-8479 Post-Quantum PeerDAS and Variable-Size Blobs](https://github.com/ethereum/EIPs/pull/12604), opened at 10:51, brings data availability sampling into the PQ upgrade scope.

**Why it matters**
- The PQ migration is not only about new signatures; the commitment schemes in the data layer need replacing as well. Both account signatures and blobs are affected, but users do not need to do anything for now.
