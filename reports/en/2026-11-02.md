## Key topics

### 1. Account protection after Binance: the account layer or the asset layer
**What happened**
- [ethresear.ch: asset-level spending limits and recovery](https://ethresear.ch/t/asset-level-spending-limits-and-recovery-should-rate-limiting-live-in-the-asset-rather-than-the-account/26205), posted at 00:15 by dlebee. Smart wallets, ERC-7579 modules, social recovery and EIP-7702 delegation all put policy in account code, and that leaves two gaps. First, a contract that already holds a `transferFrom` approval can bypass the wallet's daily limit. Second, under 7702 a stolen EOA key can re-delegate and replace the original protection. Asset-level checks cover every path that reduces a balance, and in the long run the protocol could even apply them to native ETH.
- [ERC-8474 ERC-20 Delayed Unlock discussion thread](https://ethereum-magicians.org/t/erc-8474-erc-20-delayed-unlock/30177) and [ERC-8475 ERC-20 Outgoing Window Limits discussion thread](https://ethereum-magicians.org/t/erc-8475-erc-20-outgoing-window-limits/30178), both opened at 15:55, add delayed unlocks and time-window limits at the token level.
- [Magicians: ERC-8415 and the Binance heist, what can be frozen](https://ethereum-magicians.org/t/erc-8415-and-the-binance-heist-what-can-be-frozen-and-why-rwas-need-an-asset-state-layer/30170), posted at 01:35, argues that RWAs need an asset state layer.
- [Magicians: how Arbitrum's freezes send transactions from an address without its key](https://ethereum-magicians.org/t/how-arbitrums-freezes-send-transactions-from-an-address-without-its-key/30175), posted at 13:48, breaks down the L1 transaction in which the Arbitrum Security Council froze 8,425 ETH and about 74.56 million ARB on addresses linked to the Binance incident on October 30: a 9-of-12 Safe called the UpgradeExecutor, temporarily swapped the Inbox implementation and sent the message.

**Why it matters**
- This is a direct challenge to the account abstraction roadmap: if a key can re-delegate, any policy written into the account can be swapped out. It is the gap that proposals such as EIP-8476 (permanent delegation opt-out) and EIP-8477 try to close. For users, token approvals and 7702 delegations are the two most common drain paths, so the practical steps are to clean up approvals regularly and to be careful when signing 7702 authorizations.

**What to watch**
- Whether asset-level limits become a standard that complements account-level ones (ERC-7579 modules, ERC-8403), and whether anyone turns protocol-level rate limits for native ETH into an EIP.

### 2. Transaction fees: wallet default tips are too high
**What happened**
- [potuz questions MetaMask and Rabby default priority fees](https://x.com/potuz_eth/status/2117019625296961727), 05:23: wallets default to a priority fee close to 1 gwei when a tip measured in wei would do. Scaling makes transactions cheaper, but if half the fee is the tip, the scaling work is wasted.

**Why it matters**
- When the base fee is low, what users actually pay is mostly set by the wallet's default tip. If you send transactions yourself, you can lower the priority fee by hand. Teams building wallets or SDKs should estimate it from the actual tip percentiles in recent blocks.

### 3. Post-quantum: validator PQ material registration and L2 signature aggregation
**What happened**
- [EIPs PR #12609: Add EIP-8483 Post-Quantum Material Registration](https://github.com/ethereum/EIPs/pull/12609), opened at 22:16 by potuz. It adds an EIP-7685 request type and a predeployed contract so a validator's withdrawal address can register 32 bytes of PQ material in the beacon state, preparing for a future PQ migration fork. The [EIP-8483 discussion thread](https://ethereum-magicians.org/t/eip-8483-post-quantum-material-registration/30186) opened at 22:52.
- Alongside it, [EIPs PR #12608: EIP-8148 request type moves to 0x06](https://github.com/ethereum/EIPs/pull/12608) (EIP-8148 is custom validator withdrawal thresholds) to avoid clashing with the new request type.
- [EIPs PR #12610: ML-DSA 65/87 verification vectors for EIP-8355](https://github.com/ethereum/EIPs/pull/12610), opened at 22:47. EIP-8355 is an ML-DSA signature verification precompile, one of the candidates for PQ signatures at the account layer.
- [ethresear.ch: scaling the trust with EIP-8288 on OP Stack](https://ethresear.ch/t/its-time-to-scale-the-trust-eip-8288-on-op-stack/26208), posted at 09:05. If every L2 user switched to PQ signatures, signatures would take 99% of transaction data and the transfers that fit in 6 blobs would fall from about 6,600 to about 155. With EIP-8288 (mempool signature and proof aggregation), signatures move out of the transaction and a single leanVM aggregate proof goes onchain, bringing a transaction signed with leanSPHINCS down to 100 to 129 bytes.

**Why it matters**
- Once accounts move to PQ signatures, the biggest cost is data size. Aggregation schemes like EIP-8288 decide whether PQ accounts are affordable on L1 and L2.
