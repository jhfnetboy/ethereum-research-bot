## Key topics

### 1. How big can a block get: gas limit, byte limits and FOCIL
**What happened**
- [Nero (Toni Wahrstätter) published "What's a block, and how big can it get?"](https://ethresear.ch/t/whats-a-block-and-how-big-can-it-get/26281) on 2026-11-22 at 15:32. All numbers use Glamsterdam rules with a 60M gas limit as the reference:
  - The two byte limits measure different things. EIP-7934 caps the RLP-encoded EL block at 8 MiB, and the CL caps every gossip message at 10 MiB. Since Gloas the execution payload travels on its own as a SignedExecutionPayloadEnvelope, which is roughly the EL block plus the BAL plus execution requests, and an EL-side check cannot see the last two.
  - The floor is a max, not a sum. Once a transaction is floor-bound, extra execution is free as long as intrinsic plus execution gas stays below the floor. A zero calldata byte costs 64 gas at the floor but only 4 intrinsic, leaving 60 gas of free execution.
  - The biggest block comes from zero-byte calldata plus skipped EIP-7702 authorizations. An authorization with the wrong chain ID is skipped before ecrecover, the transaction stays valid, and it only pays the 7,816 gas from EIP-2780, while each tuple can be up to 133 bytes. He built a valid block with the Amsterdam execution spec: 4 transactions, each with 234,031 zero bytes and 1,796 authorizations, using 59.96M gas and coming out at 1,892,706 bytes (1.805 MiB).
  - Break points: with Glamsterdam alone, the EL block reaches 8 MiB at 266M and the envelope passes 10 MiB at 330M. Adding EIP-8131 moves them to 514M for the EL and 339M for the envelope, so the CL breaks first. With EIP-8131 plus EIP-8279 it is 514M and 585M, and the worst envelope at 60M is 1.02 MiB. He stresses that shipping EIP-8131 without EIP-8279 widens the gap between the two limits.
  - FOCIL impact: FOCIL decides whether an IL transaction "could have been appended" using gas, nonce and balance, which stops holding once a byte limit can bind. chfast's execution-specs PR #4041 patches this by re-encoding the block and checking its RLP size, but Nero sees four problems: it misses BAL and request bytes, checking the envelope would require execution, SSZ encoding is not the EL's to compute, and it measures a block that would not actually exist.
  - His proposal: ship EIP-8131 and EIP-8279 together (the post says both are CFI'd for Hegotá), with EIP-8279 also metering deposit requests. Add one header check, gas_limit <= MAX_GAS_LIMIT, at about 500M with that pricing, or 256M if neither makes Hegotá. Let the CL bound the envelope at C + ceil(k * bid.gas_limit / 64), which with k = 1.25 is about 1.12 MiB plus C at 60M, roughly 9x smaller than 10 MiB.
- [PR #12686: EIP-8279 meters deposit request bytes](https://github.com/ethereum/EIPs/pull/12686), 2026-11-22 13:50 (nerolation). Gloas made DepositRequests an unbounded list, and each request adds 192 bytes to the payload, yet neither EIP-8131 nor EIP-8279 meters them. A relay contract calling the deposit contract in a loop, at about 26k gas per deposit, can hide under the floor of zero-byte calldata and push the payload to about 1.44 × gas_limit / 64 instead of about 1.15×. The PR meters 192 bytes when the deposit contract emits a LOG with the deposit event topic, the same condition EIP-6110 uses to turn logs into requests. Normal deposits use about 26k execution gas, well above the 12,288 extra floor gas, so they are unaffected. eth-bot shows all reviewers have approved.
- [aelowsson replied](https://ethresear.ch/t/whats-a-block-and-how-big-can-it-get/26281/2) on 2026-11-23 at 00:57. EIP-7999's approach gives each IL an equal share of the block's data limit, checked against transactions' declared data limits, so the data limit bounds the envelope independently and the gas limit can keep rising. The data resource would still need to cover authorization tuples and requests, and declaring a data limit needs a new transaction format.
- FOCIL spec sync: [PR #12702](https://github.com/ethereum/EIPs/pull/12702), 2026-11-22 23:43 (tcoratger), counts the IL's MAX_BYTES_PER_INCLUSION_LIST over the EIP-2718 encoding (a typed transaction is type || payload, not an RLP item), matching engine_getInclusionListV1 in the Engine API. [nero_eth replied to chfast](https://x.com/nero_eth/status/2124445128353874120) (11-22 17:09) that there are further issues, discussed in the FOCIL channel on Discord.

**Why it matters**
- This sets how high the gas limit can go. None of these cases is reachable at 60M today, but Nero's numbers show that moving beyond 200M requires pricing every payload byte in gas first, or the byte limits become the bottleneck.
- The most account-relevant point: the worst block exists because 7702 authorization tuples are free at the floor. Once EIP-8131 prices authorizations at 133 bytes that path closes, and batch authorizations and sponsored transactions get slightly more expensive.
- Once deposit requests are metered, staking relay contracts used in extreme ways pay more gas, while normal deposits are unaffected.

**What to watch**
- Whether EIP-8131 and EIP-8279 ship together in Hegotá, and whether a MAX_GAS_LIMIT header check is added. [ACDE #250](https://ethereum-magicians.org/t/all-core-devs-execution-acde-250-december-3-2026/30463) is set for December 3.
- When PR #12686 merges, and whether the other issues raised in the FOCIL channel make it into the spec.

### 2. EIP-7702 and account signatures: spec fixes, old key risk and PQ migration
**What happened**
- [PR #12685: EIP-7702 refund condition](https://github.com/ethereum/EIPs/pull/12685), 2026-11-22 12:41 (tcoratger). Step 7 of the spec refunds PER_EMPTY_ACCOUNT_COST - PER_AUTH_BASE_COST "if authority is not empty", while the Rationale refunds it "if the account already exists in state". The two differ for an account that exists but is empty, and the reference implementation refunds by existence, so the PR aligns step 7 with the Rationale. The author notes that after EIP-7523 no such account exists on mainnet, so mainnet behavior does not change.
- [PR #12689: EIP-7702 signed payload](https://github.com/ethereum/EIPs/pull/12689), 2026-11-22 21:04 (tcoratger). The spec says the signature is over keccak256(SET_CODE_TX_TYPE || TransactionPayload), but TransactionPayload ends with signature_y_parity, r and s, so read literally the signature covers itself. The PR lists the signed fields explicitly without the signature, as EIP-1559, EIP-2930 and EIP-4844 do. Both PRs need review from one 7702 author (adietrichs, lightclient, samwilsn, vbuterin) and one editor.
- [The EIP-8151 author replied](https://ethereum-magicians.org/t/eip-8151-account-code-restricted-ecrecover/27690/30) on 2026-11-22 at 20:14 (colinlyguo). EIP-8151 applies the EIP-3607 account-code restriction to ecRecover (except for EIP-7702 delegation indicators) and aligns with EIP-7851's 0xef0101 deactivated authorities. On the suggestion of an opt-in precompile, he said the main targets are immutable contracts like ERC-20 permit and Permit2 that hardcode calls to 0x01. If 0x01 stays unchanged, retired ECDSA keys can still drain assets through those contracts.
- PQ migration: [Vitalik replied](https://x.com/VitalikButerin/status/2124487160736973184) on 2026-11-22 at 19:56 that pretty much every non-hash-based signature scheme also uses hashes somewhere in its construction, so "depend only on curves or lattices" is not on the table. The choice is between depending only on hashes, or on hashes plus something else. [gballet](https://x.com/gballet/status/2124623820497555591) said at 11-23 04:59 that figuring out how to upgrade Ethereum's signature scheme is more urgent than choosing the specific scheme. [decentrek](https://x.com/decentrek/status/2124603905833324867) answered a question at 11-23 03:40: EIP-8130 itself can support PQ signatures, but Base has not said whether it will support leanSPHINCS, another PQ scheme, or both.

**Why it matters**
- EIP-7702 is already live, and both fixes bring the spec text in line with the reference implementation without changing mainnet behavior. They still matter for new clients and auditors, since a literal reading could produce the wrong refund or signing hash.
- EIP-8151 highlights a practical account migration problem: after an EOA moves to a new signature scheme, the old ECDSA key can still authorize transfers through permit-style contracts. Migration has to deal with 0x01 at the protocol level, and wallets should prompt users to revoke permits and approvals tied to old keys.
- Vitalik's reply narrows the PQ choice to "pure hash" versus "hash plus other assumptions", consistent with the "PQ signature plus EC signature" dual signature idea Dankrad raised last time.

**What to watch**
- Author reviews on PR #12685 and #12689, and whether EIP-8151 enters upgrade discussions.
- [PQ-CL Breakout #4](https://ethereum-magicians.org/t/pq-cl-breakout-4-november-24-2026/30460) is set for November 24.

### 3. Privacy and account abstraction: the 4337 relay path, a Frame transaction privacy pool and agent account safety
**What happened**
- [kassandra on 4337 privacy relaying](https://x.com/kassandraETH/status/2124492676984619502), 2026-11-22 20:18: routing privacy protocol withdrawals and transactions through the 4337 relay path means freedom and choice, since 4337 bundling is general-purpose infrastructure and many services bundle UserOps. [She added at 20:33](https://x.com/kassandraETH/status/2124496532896678166) that if you do not want to depend on protocol-specific relayers being available, or on their rules and fees, account abstraction is the way out: 4337 bundling today, Frame transactions tomorrow.
- In a discussion with anondotinc, [kassandra said at 22:27](https://x.com/kassandraETH/status/2124525150917820748) that the 4337 relay path with a paymaster can give strong privacy. [At 23:38](https://x.com/kassandraETH/status/2124543144742011223) she noted that if leaking "the same user is moving WETH (the fee) plus other assets" is unacceptable, the fee UTXO can be ZK-proven, which works but adds gas. [At 11-23 00:02](https://x.com/kassandraETH/status/2124549166827246062) she added that Railgun unshields always carry this commitment token tagging property.
- [New reply on the Frame transaction privacy pool thread](https://ethresear.ch/t/a-privacy-pool-on-frame-transactions-what-works-and-the-case-that-does-not-yet/26223/5), 2026-11-22 19:27. The original post (11-06, Nethermind) ran a BN254 Groth16 privacy pool on Frame transactions with withdrawals at 679,322 gas and no relayer, but the proof check exceeds the validation gas cap and the pool cannot make a call from the user's own address. liamwilliams said the EOA case is real for identity-bound actions (claiming airdrops, voting or delegating, renewing names), but rare and concentrated around claim events, so it should be treated as a compatibility feature and claim and vote flows measured before raising the verify budget for it.
- Agent account safety reviews continued. [Secrypta's review of Policy-Enforced Agent Accounts](https://ethereum-magicians.org/t/draft-erc-policy-enforced-agent-accounts/30467/4) (11-22 17:32) noted that most drains do not touch the policy at all. Funds leave through authority granted earlier and never revoked: ERC-20 allowances or permits, operator approvals, installed modules or executors, and for 7702 accounts the delegation target itself. Secrypta suggested the evidence layer expose 7579 executors and the current 7702 delegation target. [Zealynx checked the reference registry](https://ethereum-magicians.org/t/draft-erc-policy-enforced-agent-accounts/30467/5) (11-23 04:53) and confirmed that declare takes effect in the same block, so a signer swap is equivalent to loosening the policy to anything, and declare should respect the minimum delay too.
- [ERC-8507 Agent Allowlist Framework released 0.2.0](https://ethereum-magicians.org/t/erc-8507-agent-allowlist-framework-aaf/30456/4) on 2026-11-23 at 00:46. The draft got its number and a new name, and following review it adds a per-action reuse policy (NONE, WHILE_CURRENT, ADMISSION, defaulting to NONE). Earlier, [Secrypta](https://ethereum-magicians.org/t/erc-8507-agent-allowlist-framework-aaf/30456/2) (11-22 17:31) warned that an EIP-7702 account can re-delegate at any time, changing code without changing address, so an allowlist entry should optionally pin the delegation target or code hash it was assessed with.

**Why it matters**
- Someone has to pay gas for a privacy protocol withdrawal. Using general 4337 bundling, or Frame transactions later, frees users from protocol-run relayers, which is the most direct way "privacy plus AA" reaches users. Keeping the fee output from linking activity is the next implementation problem.
- The agent account reviews keep landing on the same point: the 7702 delegation target and previously granted approvals are the real exits for funds, and checking the policy commitment alone is not enough.

**What to watch**
- Whether the Frame transaction validation gas cap is raised for privacy pools (the MAX_VERIFY_GAS discussion from earlier issues).
- Developers running agents on 7702 or modular accounts: audit allowances, permits and installed modules regularly, and record the current delegation target.
