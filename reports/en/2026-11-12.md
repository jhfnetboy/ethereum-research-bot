# Ethereum Research Daily 2026-11-12

Keywords: pqai27, post-quantum, Hegotá, Frame Transactions, EIP-8288

Summary: Ethlabs posted its pqai27 proposal on Ethereum Magicians, arguing that Ethereum should become post-quantum and post-AI hardened in 2027. Hegotá would prioritize Frames and post-quantum accounts, FOCIL would step aside, and Ethlabs is withdrawing quick slots. ## Highlights
1. Ethlabs published pqai27, a proposal for Ethereum to be post-quantum and post-AI ready in 2027. On the execution layer, Hegotá would ship Frames with SPHINCS post-quantum signatures plus post-quantum account EIPs, FOCIL should not slow that goal down, and Ethlabs is pulling quick slots out of Hegotá.
2. The proposal gets a brief discussion at tonight's ACDC #191 at 21:00, alongside whether EIP-8483 (post-quantum material registration) goes into Hegotá.
3. Account abstraction saw four revisions overnight: EIP-8141 clarifies when a transaction is invalid before execution, EIP-8250 lets single-use keyed transactions pass static and mempool checks, EIP-8151 adds public mempool rules for recovered signers, and EIP-8288 supports batched signature claims.
4. Also new: a draft EIP adds code reads to block-level access lists (BAL), and ETHBEAT listed the private payments app Tacit Pay with a red trusted setup rating.

## Key topics

### 1. pqai27: Ethlabs wants post-quantum and post-AI hardening done in 2027
**What happened**
- [Ethlabs: An Ethlabs view on post-quantum and post-AI timelines: pqai27](https://ethereum-magicians.org/t/an-ethlabs-view-on-post-quantum-and-post-ai-timelines-pqai27/30351) Posted on Magicians at 03:51 on 2026-11-12. The core claim is that Ethereum should reach "pqai-ready" in 2027: consensus is post-quantum and every user has a post-quantum migration path for their account, while keeping the capacity Glamsterdam delivers. "pqai-scaled", with post-quantum transactions and blobs at full capacity, is the stretch goal for 2027.
- The draft plan for Hegotá: the execution layer ships Frames plus SPHINCS post-quantum signatures plus post-quantum account EIPs, and without FOCIL it can ship on its own without waiting for the consensus layer. The consensus layer starts on post-quantum consensus, either a post-quantum Gasper or decoupled consensus, which is still undecided. The following "I" upgrade would bring post-quantum DA (EIP-8479) and signature aggregation (EIP-8288), possibly with FOCIL. (Same source, 2026-11-12)
- The post says Glamsterdam ships as planned and Frames sits on the critical path for pqai27. Ethlabs is withdrawing quick slots from Hegotá and will push for quicker slots in 2028 instead. (Same source, 2026-11-12)
- [Ethlabs announces pqai27 on X](https://x.com/ethlabs_org/status/2120621682889052345) At 03:56 on 2026-11-12, framed as input into Ethereum's governance process.
- [Barnabé: reprioritizing means giving up proposals dear to us](https://x.com/barnabemonnot/status/2120633537464316150) At 04:43 on 2026-11-12, noting that the post-quantum work also brings new pq-ready accounts built on Frame Transactions.
- [Caspar asks to discuss pqai27 on the ACDC #191 agenda](https://github.com/ethereum/pm/issues/2291) Comment posted at 06:49 on 2026-11-12.

**Why it matters**
- For the account track this is a direct boost. In this plan Frames (EIP-8141) goes from one of Hegotá's headliners to the thing that has to ship first, and migrating accounts to post-quantum becomes the main job for wallets and the AA ecosystem. The post also names account features to roll out along the way: key rotation, separating recovery keys from execution keys, and scoped access.
- The cost is just as clear: FOCIL (censorship resistance) and quick slots (faster blocks) get pushed back, and Hegotá's scope could change a lot.
- For users, post-quantum transactions become available once Ethereum is pqai-ready, but larger signatures make them more expensive. Costs only get close to normal transactions with pqai-scaled and signature aggregation. (Same source)

**What to watch**
- How core developers react at ACDC #191 tonight at 21:00, and whether any client team publicly backs or opposes moving FOCIL aside.
- Whether post-quantum consensus means retrofitting Gasper or switching to decoupled consensus, which the post calls the biggest open question.
- Whether wallet and AA teams start planning post-quantum account migration tools on top of Frames.

### 2. Account abstraction and transactions: four overnight changes across the Frames EIPs
**What happened**
- [EIP-8141 note: when a SENDER frame makes a transaction invalid before execution](https://github.com/ethereum/EIPs/pull/12656) Opened at 07:12 on 2026-11-12. Only a frame flagged APPROVE_EXECUTION can set sender_approved, so a SENDER frame with no such frame before it always fails, and builders and mempools can drop the transaction without executing anything.
- [EIP-8250 update: single-use keyed transactions pass static and mempool checks](https://github.com/ethereum/EIPs/pull/12659) Opened at 07:12 on 2026-11-12. When nonce_seq equals MAX_NONCE_SEQ and every selected key reads zero, the transaction counts as executable rather than a nonce overflow. Replay protection is unchanged.
- [EIP-8151 update: public mempool rules for recovered signers](https://github.com/ethereum/EIPs/pull/12653) Opened at 01:20 on 2026-11-12. Under EIP-8151, ecRecover reads the recovered address's code, so an EIP-8141 validation prefix can depend on a third-party account. This PR adds the matching mempool rules.
- [EIP-8288 update: batched generic signature claims](https://github.com/ethereum/EIPs/pull/12654) Opened at 04:49 on 2026-11-12. One user-selected batch program can prove claims for several transactions and signature schemes at once. The PR puts the cost at 30,000 intrinsic proof-share gas plus 3,000 verification gas per claim.
- [EIP-8288 update: use the EIP-8141 leanSPHINCS scheme id in dependency triples](https://github.com/ethereum/EIPs/pull/12657) Opened at 07:12 on 2026-11-12, so one leanSPHINCS key carries the same number (currently 0x3) in both EIPs.
- [New draft EIP: eth/73 proof wrapper propagation](https://github.com/ethereum/EIPs/pull/12655) Opened at 04:50 on 2026-11-12. Building on EIP-8288, it lets raw signatures go straight to aggregators without first producing a STARK.

**Why it matters**
- This is concrete spec work on the pqai27 critical path. EIP-8141 is Frames itself and EIP-8288 is post-quantum signature aggregation, and unifying their SPHINCS ids shows the two specs being lined up.
- The mempool rules in EIP-8141, EIP-8151 and EIP-8250 decide whether smart account transactions can travel safely through the public mempool, which is the most underrated part of getting native AA live.

**What to watch**
- Frame Transaction Breakout #8 on 11/17 ([pm #2295](https://github.com/ethereum/pm/issues/2295)), and whether pqai27 changes the scope of Frames, since the proposal mentions possible lighter variants.

### 3. Infrastructure: code reads in BAL, and a case for elastic capacity
**What happened**
- [New draft EIP: Code Reads in Block-Level Access Lists](https://github.com/ethereum/EIPs/pull/12658) Opened by LukaszRozmej at 07:12 on 2026-11-12. It adds a code_hash to EIP-7928's AccountChanges, so the BAL names every piece of pre-block state a block reads and a stateless client or prover can build its input from the block, the BAL and a state snapshot without executing the block. The [Magicians discussion thread](https://ethereum-magicians.org/t/code-reads-in-block-level-access-lists-extension-to-eip-7928/30354) opened at 07:14 on 2026-11-12.
- [ethresear.ch: Elastic Ethereum](https://ethresear.ch/t/elastic-ethereum/26236) An opinion post by cskiraly at 18:40 on 2026-11-11. It argues for adjusting capacity to measured resource pressure, the way TCP congestion control does, instead of a fixed gas limit plus a safety margin. Citing mainnet data, it says the median block reaches 95% of reporting nodes 0.38 seconds after it is first seen (0.70 seconds for the 99th percentile block).

**Why it matters**
- BAL is one of Glamsterdam's core changes. Adding code reads makes stateless validation and zk proving easier, which ties directly into raising the gas limit.
- Elastic capacity is a different way to think about setting the gas limit. For now it is a research view with no EIP behind it.

**What to watch**
- Whether the code read extension gets proposed for inclusion in EIP-7928 for Glamsterdam.
