## Key topics

### 1. Getting frame transactions and EIP-8037 ready
**What happened**
- [ethrex: a public testnet for the EIPs behind Ethereum's privacy roadmap](https://x.com/ethrex_client/status/2095897077955899638), 22:29, built on Glamsterdam and running EIP-8141 (frame transactions), EIP-8250 (keyed nonces), EIP-8272 (recent roots), EIP-7805 (FOCIL) and EIP-8369 (VOPS profiles), each implementation up to date.
- [EIP-8037: restore a frame's state gas on rollback](https://github.com/ethereum/EIPs/pull/12256) was merged (chfast). The rule said rollbacks refill the state gas "charged within the frame", but no counter held that quantity; the PR introduces the frame's starting reservoir so two frames with equal counters cannot revert owing different amounts.
- [EIP-8037: return state gas to gas_left when a child merges](https://github.com/ethereum/EIPs/pull/12265) was merged (chfast). The rationale promised execution gas would never be stranded in the reservoir, but the rules did not deliver: two sibling calls, the shape of an ERC-4337 bundle, are enough for the first call's write to a fresh slot to spill 97,920 from `gas_left` while the second call's clearing refund lands in the reservoir.
- [EIP-8037: remove stale EIP-7610 collision rules](https://github.com/ethereum/EIPs/pull/12296); [EIP-2780: align runtime charging and reference cases](https://github.com/ethereum/EIPs/pull/12080), merged, which also charges delegation-target access for self-transfers from 7702-delegated accounts, matching EELS and geth.
- [EIP-8130: rename to Keystore Accounts](https://github.com/ethereum/EIPs/pull/12295) was merged; it was previously "Account Abstraction by Account Configuration", with no spec or wire-format changes.

**Why it matters**
- The privacy-related EIPs can now be tried together on one testnet, so wallets and privacy protocols can start integration testing. The ongoing patches to EIP-8037's cross-frame accounting show how complex the state gas reservoir is across nested calls, which is exactly where the later security issues came from.

### 2. AI agent signing
**What happened**
- [New ERC: declarative wallet signing policy](https://github.com/ethereum/ERCs/pull/1994) (moodysalem, ERC-8411), stating in advance which transactions a wallet may sign without asking a human through an ordered list of `allow`, `review` and `deny` rules over each planned call, the transaction envelope and the request channel.
- [New ERC: agent wallet execution interface](https://github.com/ethereum/ERCs/pull/1995) (ERC-8412), for AI agents, scheduled jobs and other clients that cannot approve on their own to submit and track transactions; the same batch included [ERC-8410 portable execution plan artifact](https://ethereum-magicians.org/t/erc-8410-portable-execution-plan-artifact/29587).

**Why it matters**
- Automatic signing by agents is either unsafe or unscalable, and a policy written in advance is a middle ground. These PRs are currently closed, but the direction is worth following.
