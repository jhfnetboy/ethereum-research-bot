## Highlights
1. **Vitalik's position**: no need to migrate assets today, but minimize exposure to cryptography that is quantum-vulnerable and possibly AI-vulnerable. For multisigs, the ideal is for each signer to change keys after every operation.
2. **EIP-8288**: transactions can depend on post-quantum signatures (leanSPHINCS) and STARK proofs (leanSTARK) verified outside the EVM, with one recursive STARK per block.
3. **AA spec changes**: EIP-8130 keeps only the Keystore and its transaction type moves to a new EIP (EIP-8430). Frame modes are now checked against a set of valid values, EIP-7906 adds a POST_TX mode, and keyed nonces are recorded in the BAL.
4. **Starknet weighs going independent as an L1**: StarkWare thinks Ethereum's security roadmap is not moving fast enough.

## Key topics

### 1. Post-quantum and privacy: EIP-8288 and Vitalik's response
**What happened**
- [Vitalik: I don't recommend anyone scramble to move their funds to new wallets today](https://x.com/VitalikButerin/status/2107976296320106851), 06:28, but the risks to cryptography from AI-accelerated math deserve serious attention, not just quantum. [Correction: for multisigs, the ideal "safe" rule is that each signer changes their key after each operation](https://x.com/VitalikButerin/status/2108046549020557482), 11:07.
- [ethresear.ch: exposing an ISA for post-quantum proofs on Ethereum](https://ethresear.ch/t/exposing-an-isa-for-post-quantum-proofs-on-ethereum/26136), 22:34 (soispoke, [post](https://x.com/soispoke/status/2108225737991795099) at 22:59). EIP-8288 lets transactions depend on leanSPHINCS signatures and leanSTARK proofs declared in the dependency frame of an EIP-8141 frame transaction. Nodes check them before forwarding, and each block carries one recursive STARK proving all its dependencies valid. Today's privacy pools verify Groth16 proofs in-contract with the BN254 pairing precompile, which a quantum computer that breaks BN254 could forge. With EIP-8288, the pool contract only checks that the transaction depends on a proof for its own circuit with the expected public inputs. The post compares the EVM, RISC-V and an eISA designed for proving.
- [binji: Hegotá's Frames make every account cryptographically agile, so all of them can become post-quantum](https://x.com/binji_x/status/2107971096750305611), 06:07.

**Why it matters**
- For privacy apps, proof verification moves from an in-contract precompile to the protocol layer, which is both quantum-safe and aggregatable, so the per-transaction cost of privacy pools could drop. For users, the most practical step for now is to limit public key exposure, especially for multisigs and large accounts.

### 2. AA specs: splitting EIP-8130 and tightening frame transactions
**What happened**
- [EIP-8130 PR: scope to the Keystore and move the transaction type to a new EIP](https://github.com/ethereum/EIPs/pull/12386) was merged (chunter-cb). [Ethereal news's roundup](https://x.com/EtherealnewsHQ/status/2107920083997876441), 02:44, lists the new EIP-8430 account abstraction transaction type (split out from EIP-8130) and EIP-8425, quantum freeze and account recovery.
- EIP-8141 (frame transactions): [frame modes checked against a set of valid values](https://github.com/ethereum/EIPs/pull/12453) was merged (lightclient); [roll back the approval context when a call reverts](https://github.com/ethereum/EIPs/pull/12458) was submitted (soispoke).
- [EIP-7906: assign opcode bytes and add POST_TX to the valid frame modes](https://github.com/ethereum/EIPs/pull/12454) was merged; [clarify diff opcode semantics and gas accounting](https://github.com/ethereum/EIPs/pull/12461) was submitted.
- [EIP-8250: record keyed nonces in the block access list](https://github.com/ethereum/EIPs/pull/12457) was merged (nerolation); [EIP-3298: remove the refund cap from frame transaction settlement](https://github.com/ethereum/EIPs/pull/12455) was merged.
- [Descriptor Attestations for ERC-7730](https://github.com/ethereum/ERCs/pull/1576) was merged, adding attestations to Clear Signing descriptor files.

**Why it matters**
- Separating the Keystore from the transaction type gives native AA two tracks that can move independently. Frame transactions are settling one piece at a time (POST_TX assertions, keyed nonces, refund settlement), so wallets can start prototyping against the frames-devnet spec.
