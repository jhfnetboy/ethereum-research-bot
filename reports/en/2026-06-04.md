## Key topics

### 1. EIP-8130: from owner to scoped actor
**What happened**
- [EIP-8130: rename owner to actor and finalize Transaction Context naming](https://github.com/ethereum/EIPs/pull/11764) (chunter-cb), submitted and merged. Many signing entities are scoped credentials (PAYER only, SIGNATURE only, session style keys), so "owner" overstated their authority; `ownerId`, `OwnerConfig`, `authorizeOwner` and similar become `actorId`, `actor_config`, `authorizeActor` and so on.
- [EIP-8130: rename `IAccountConfiguration.verify` to `verifyActor`](https://github.com/ethereum/EIPs/pull/11765), submitted and merged.
- [EIP-8130: add actor call policies and per-actor expiry](https://github.com/ethereum/EIPs/pull/11766), submitted and merged. A `policyType` byte in `actor_config` selects an optional call policy, with a signed `commitment` and a `manager` stored in policy slots keyed by `(account, actorId)`. Enforcement happens at execution, not validation: the protocol never reads the policy slots when deciding validity, so policies stay off the mempool validity surface.

**Why it matters**
- For wallets and dapps: limited permissions such as session keys and payer-only keys get a common name and an expiry mechanism. Because policies only apply at execution, the cost for nodes to validate a transaction does not grow with policy complexity, which is the tradeoff between mempool safety and flexibility in native AA design.

### 2. The account ecosystem around frame transactions
**What happened**
- [ERC: Modular Accounts for Frame Transactions](https://github.com/ethereum/ERCs/pull/1794) (chiranjeev13), submitted, with a [Magicians thread](https://ethereum-magicians.org/t/erc-8286-modular-accounts-for-frame-transactions/28695) at 06:35; this is ERC-8286. It leaves the ERC-7579 module structure unchanged and only defines the validation flow for EIP-8141 frame transactions: a validator module returns an approval mode, and the account applies it with the APPROVE instruction during a VERIFY frame.
- [Magicians: EIP-8282 Builder Execution Requests](https://ethereum-magicians.org/t/eip-8282-builder-execution-requests/28699), 14:40 (wemeetagain). It gives EIP-7732 (ePBS) builders their own execution layer request contracts on the EIP-7685 request bus, rather than routing them through the validator deposit and exit flows.

**Why it matters**
- For smart account teams: existing ERC-7579 modules can carry over to native AA, lowering migration cost.

### 4. ACDE #238
**What happened**
- Per Ethereal news #26, ACDE #238 (21:00): glamsterdam-devnet-5 is live (the devnet-4 spec plus EIP-8045, which excludes slashed validators from proposing); bal-devnet-7 was the last execution layer focused devnet; glamsterdam-devnet-6 targets about two weeks out with the remaining execution layer EIPs (EIP-7997 deterministic factory, EIP-8246 removing the SELFDESTRUCT burn) and preliminary repricing numbers. Hegotá non-headliners proposed include data repricing (EIP-8131 adding auth data to the EIP-7623 floor, EIP-8279 a block access list byte floor), EIP-7979 call and return opcodes, and EOA migration to smart accounts (EIP-7851 code controlled EOA delegation, EIP-8151 an ecRecover aware of ECDSA authority deactivation), with set code discussed as a broader alternative. EIP-8222 lean staking presented staking deposits and withdrawals through a privacy pool.

**Why it matters**
- For accounts: EIP-7851 and EIP-8151 address what EIP-7702 left open: once an EOA delegates to code, can its original key be deactivated, and how does ecRecover know. That decides whether an EOA can truly become a smart account.
