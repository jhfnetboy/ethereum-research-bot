### 2. EIP-8141: passkeys and mempool admission
**What happened**
- [EIP-8141: a canonical P256 sender account for no-simulation admission](https://github.com/ethereum/EIPs/pull/12004) (AnkushinDaniil), submitted. 8141's protocol-defined no-simulation admission paths (default code, the canonical paymaster, the expiry verifier) are SECP256K1-only, while passkey/WebAuthn (secp256r1) wallets are a large and growing share of smart accounts; today an EIP-7702-delegated P256 account must go through full validation prefix simulation. The PR adds a canonical P256 sender account recognized by runtime code match, admitted with a code match, one `P256VERIFY` and a scope check.
- [EIP-8141: allow direct evaluation of protocol-defined validation prefixes](https://github.com/ethereum/EIPs/pull/12001) (svlachakis), submitted. Default code, the canonical expiry verifier and the canonical paymaster have no deployed code to discover by execution, so for prefixes made only of them, simulation and direct evaluation are the same computation; the common flows, `self_verify` EOA-style transactions and canonical-paymaster-sponsored transactions, fall into this class.
- [EIP-8141: specify the APPROVE opcode gas cost](https://github.com/ethereum/EIPs/pull/12003) (AnkushinDaniil), submitted, since `APPROVE` (`0xaa`) was the only new frame opcode without a gas cost; [bound the fee fields in the static constraints](https://github.com/ethereum/EIPs/pull/12005) (svlachakis), submitted, since RLP admits arbitrarily long integers while `TXPARAM` pushes fee fields onto the stack, where they might not fit a stack word.

**Why it matters**
- For passkey wallets: if the canonical P256 account is adopted, passkey accounts can use the same fast admission path as EOAs, without the mempool limits that full simulation brings. For nodes: common transactions skip simulation, shrinking the DoS surface of the native AA mempool.

### 3. State migration and privacy
**What happened**
- [New EIP: offline state migration to the PBT](https://github.com/ethereum/EIPs/pull/12006) (misilva73), submitted; per Ethereal news #32 it is numbered EIP-8347. State at a finalized anchor block is converted offline from the hexary MPT to the Partitioned Binary Tree (EIP-8297) and distributed as a verifiable snapshot; nodes verify it against the anchor's `stateRoot` and catch up to the tip by replaying BALs (EIP-7928).
- [EIP-8297: redraw diagram and drop the EIP-7864 changes section](https://github.com/ethereum/EIPs/pull/12002), submitted and merged.
- [StarkWare: open-sourced the formal verification of the STRK20 privacy pool, with 230+ machine-checked theorems](https://x.com/StarkWareLtd/status/2080277557967298987), 20:03.
