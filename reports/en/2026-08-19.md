## Key topics

### 1. The expiry mechanism for frame transactions
**What happened**
- [EIP-8141: make the expiry frame a new mode](https://github.com/ethereum/EIPs/pull/12198) (nerolation), submitted. The PR says this is what the spec would look like if expiry reverted from a special-target VERIFY frame to a new frame mode.
- [EIP-8141: state that installing the expiry verifier leaves the nonce](https://github.com/ethereum/EIPs/pull/12203) (Marchhill), submitted. The spec only requires installing the expiry verifier runtime code at `EXPIRY_VERIFIER` at activation, leaving the account nonce open; other system contract predeploys sit at nonce 1, but there it follows from the deployment mechanism rather than being a chosen value, as EIP-2935 says directly.
- [EIP-8130: adoption profiles, bounded auth gas and timestamp normalization](https://github.com/ethereum/EIPs/pull/12204) (chunter-cb), resubmitted as a new version.

**Why it matters**
- An expiry time keeps a signed transaction from being included unexpectedly long afterwards, a safety feature of native AA; how it is implemented decides whether a mempool can cheaply tell that a transaction has expired.

### 2. Data floors and cross-chain confirmation
**What happened**
- [EIP-8131: data floor independent from the gas limit](https://github.com/ethereum/EIPs/pull/12200) and [EIP-8279: BAL floor independent from the gas limit](https://github.com/ethereum/EIPs/pull/12201) (nerolation), submitted, clarifying that they enable a gas limit increase but do not depend on one.
- [Derek Chiang: it is ironic that Base bridges faster to Solana than to Ethereum](https://x.com/decentrek/status/2090072410376769750), 20:44. The Base to Ethereum bridge runs a multi-prover model where, if a TEE and a ZK prover agree on Base's state transitions, a state update settles on Ethereum in one day.

**Why it matters**
- L2 to L1 withdrawals still take days, the most visible interop gap for users and the practical backdrop for FCR, faster slots and similar proposals.
