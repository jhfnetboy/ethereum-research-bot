## Key topics

### 1. Post-quantum accounts: concrete specs for signature aggregation and key derivation
**What happened**
- [EIP-8288 merged: the leanSPHINCS public key is now PK.seed || PK.root](https://github.com/ethereum/EIPs/pull/12666), merged 2026-11-14 04:48. Author VanshSahay notes that EthLib and leanVM both moved leanSPHINCS to the FIPS 205 layout and dropped the old public parameter. He caught the mismatch while implementing the scheme in go-ethereum, where the known-answer tests from both projects only pass with the new order.
- [New EIP draft: Generic Proof Verification and Batching](https://github.com/ethereum/EIPs/pull/12664), opened by Marchhill on 2026-11-13 19:21 and still being revised at 2026-11-14 05:00. It turns on EIP-8288's reserved LEANSTARK_SCHEME and adds sponsored batch proofs: a sponsor pays once per batch leaf, member transactions pay per claim, and any valid subset can be included without members signing again. Discounted claims go builder-direct only, while ordinary single proofs stay eligible for the public mempool. The PR says every gas value and bound is provisional, and activation requires measured full-block completion time and memory on stated hardware.
- [EIP-8288 batched leanSTARK claims PR closed](https://github.com/ethereum/EIPs/pull/12654) around 2026-11-14 05:28 without merging; its description says the new draft above supersedes it.
- [ERC-8499: Hash-Based Key Derivation from BIP-39](https://ethereum-magicians.org/t/erc-8499-hash-based-key-derivation-from-bip-39/30375), thread opened by johba on 2026-11-13 17:34 ([ERC PR #2172](https://github.com/ethereum/ERCs/pull/2172) followed at 17:41). It covers leanSPHINCS, SLH-DSA, WOTS, FORS and XMSS. The author lays out today's split: some wallets derive from the BIP-39 entropy with Keccak-256, some run a second PBKDF2, and some apply HMAC-SHA512 to the BIP-39 seed, so one phrase gives different keys in different wallets. A reply at 2026-11-14 02:38 adds that after a parameter-set change, a restoring wallet derives every key type it supports and checks which one the account accepts, and it must keep deriving retired key types because the account address may have come from the old key.
- [EIP-8310 post-quantum keystore thread](https://ethereum-magicians.org/t/eip-8310-post-quantum-keystore-for-stateful-keys/28853): at 2026-11-14 03:09 johba asked whether an XMSS seed can be recovered from a mnemonic if the keystore file is lost, the way ERC-2333 works for BLS. ERC-8499 deliberately does not rebuild stateful keys from a phrase.

**Why it matters**
- EIP-8288 is what makes post-quantum signatures cheap enough onchain. A single leanSPHINCS signature is large, so aggregation and batch proofs set the per-transaction cost of a post-quantum account. The key format mismatch only surfaced during a geth implementation, a sign the spec is now reaching client code.
- ERC-8499 is the most user-facing piece. If wallets derive keys differently, restoring the same phrase in another wallet may not recover the same post-quantum account.
- Stateful signatures (XMSS, WOTS) can use each leaf only once, and losing state opens the door to forgeries. That is why ERC-8499 does not rebuild stateful keys from a phrase.

**What to watch**
- An EIP number, discussion thread and benchmark results for the new batching draft.
- The [EIP-8141 PR adding leanSPHINCS](https://github.com/ethereum/EIPs/pull/12616) was updated at 2026-11-14 04:20 and is still open. Which post-quantum scheme Frame transactions adopt depends on it.

### 2. Account abstraction and the mempool: validation dependencies and delegation rules for Frame transactions
**What happened**
- [EIP-8151 adds public mempool rules](https://github.com/ethereum/EIPs/pull/12653), with a revision pushed at 2026-11-13 13:44 and an author reply to review at 16:00. Background: EIP-8151 makes ecRecover read the recovered address's code, so an EIP-8141 Frame transaction whose validation prefix calls ecRecover can depend on a third-party account. The new rules record each recovered address and its code class (empty or delegated, versus other code) as a signer dependency and revalidate when the class changes. They cap pending transactions per recovered address, with separate shares for the canonical signature hash and other digests, and count pay-frame recoveries once per paymaster.
- [EIP-8430 (AA Transaction Type) new commit: a delegation entry requires nonce_key 0](https://github.com/ethereum/EIPs/pull/12385), pushed 2026-11-13 21:49. EIP-8430 supports 2D nonces where key 0 is the account's normal nonce, and this rule ties in-transaction EIP-7702-style delegation to that main nonce sequence.
- [EIP-8497: FOCIL omission witnesses for Frame transactions](https://github.com/ethereum/EIPs/pull/12663) got two revisions at 2026-11-13 17:58 and 19:44 (weighting writers by listing count, proving equivocators). Correction: yesterday's report called this draft EIP-8500. The file in the PR is eip-8497.md, and Ethereal news #47 also lists it as EIP-8497.

**Why it matters**
- Smart account transactions depend on onchain state for validity, so nodes need to know which account change can invalidate a pending transaction. Without that, an attacker can cheaply invalidate many mempool transactions at once. EIP-8151's rules bear directly on whether Frame transactions can safely use the public mempool.
- Requiring nonce_key 0 for delegation stops an account from quietly changing its code delegation through a parallel nonce lane. Wallets implementing 2D nonces should account for this.

**What to watch**
- Frame Transaction Breakout #8 on November 17 ([pm #2295](https://github.com/ethereum/pm/issues/2295)).
- Whether Hegotá keeps FOCIL, which decides whether EIP-8497 is needed at all.

### 3. Hegotá scope and gas repricing
**What happened**
- [Toni Wahrstätter: core devs may revisit Hegotá scope in about two weeks](https://x.com/nero_eth/status/2121181295103377865), 2026-11-13 17:00. The question is whether a narrower post-quantum focus would move faster; reconsidering FOCIL and features that scale or shorten slots would be a significant step.
- [Barnabé: pqai27 is an Ethlabs proposal, not a ratified consensus](https://x.com/barnabemonnot/status/2121158282593083855), 2026-11-13 15:28, cautioning against reading a roadmap proposal as already approved.
- [Ethereal news weekly #47](https://ethereal.news/ethereal-news-weekly-47/), published 2026-11-13, records that Ethlabs withdrew quick slots (EIP-8198) to focus on post-quantum and it is now DFI; that the Mumbai workshops put the Q-day estimate at 2029, down from 2032 a year ago; that Dedaub, ChainSecurity and the EF will present EIP-8037 and EIP-8038 audit findings at ACDT #103 on November 16, with next steps (spec changes or Hoodi scheduling) at ACDE #249 on November 19; and new EIPs including EIP-8487 (separate execution credits and billing credits) and EIP-8488 (versioned opcodes for gas repricing).
- [PQ-CL Breakout #1](https://github.com/ethereum/pm/issues/2304) was filed at 2026-11-14 04:28: a post-quantum consensus layer working session, first meeting November 17 at 21:00 for 120 minutes, configured to recur every Tuesday, Wednesday and Friday.
- [ladislaus: post-quantum will make today's repricing debate look small](https://x.com/ladislaus0x/status/2121251993507299762), 2026-11-13 21:41, pointing to ecrecover, permits and immutable contracts as bigger compatibility problems in a post-quantum migration.

**Why it matters**
- If Hegotá narrows to post-quantum, Frame transactions and post-quantum signatures get priority while FOCIL and shorter slots may slip, which affects censorship resistance and how fast users see confirmations.
- EIP-8037 (state growth gas) and EIP-8038 (state access gas) change contract call costs directly. App developers should watch the November 16 audit findings, and Hardhat can already test against them.

**What to watch**
- Audit findings at ACDT #103 on November 16 and the decision at ACDE #249 on November 19.
- The first PQ-CL session on November 17, and whether the November 26 ACDC settles FOCIL.
