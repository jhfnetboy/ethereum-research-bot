## Highlights
1. **EIP-8288 renamed**: from describing frame modes to describing the goal directly, signature and proof aggregation in the mempool.
2. **Dependency verification frames**: the spec now covers the aggregation circuit, frame placement, receipts and atomic batches.
3. **Paymaster admission**: non-canonical paymasters are capped at one pending transaction today, and a PR proposes judging them by egress properties instead.

## Key topics

### 1. Mempool rules for aggregation and paymasters
**What happened**
- [EIP-8288: new title](https://github.com/ethereum/EIPs/pull/12327) (vbuterin) was merged, changing it to "In-mempool signature and proof aggregation", because a title about the goal beats one about frame modes, an implementation detail.
- ilitteri's series of PRs: [the aggregation circuit's required properties](https://github.com/ethereum/EIPs/pull/12323), [where a dependency verification frame may sit](https://github.com/ethereum/EIPs/pull/12324), [the dependency verification frame's receipt](https://github.com/ethereum/EIPs/pull/12325) and [excluding dependency verification frames from atomic batches](https://github.com/ethereum/EIPs/pull/12326).
- [EIP-8141: admit paymasters by a node-decidable egress property](https://github.com/ethereum/EIPs/pull/12328) (AnkushinDaniil, later closed). Today a paymaster either exactly matches the canonical code or is treated as non-canonical and capped at one pending transaction, a cap that exists only because a non-canonical paymaster's ETH egress is uncontrolled.

**Why it matters**
- Paymaster rules decide whether sponsorship services can run at scale in the public mempool, and the more concrete the aggregation spec, the sooner clients can implement it.
