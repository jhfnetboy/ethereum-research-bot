## Key topics

### 1. Native AA and privacy: EIP-8250
**What happened**
- [soispoke: new EIP-8250, Keyed Nonces for Frame Transactions, replacing the single sender nonce with (nonce_key, nonce_seq) to give frame transactions independent replay domains](https://x.com/soispoke/status/2051632978942390479), 18:59; [Magicians discussion](https://ethereum-magicians.org/t/eip-8250-keyed-nonces-for-frame-transactions/28437), 15:38: nonce_key 0 aliases the legacy account nonce, and each non zero key selects an independent sequence stored in a NONCE_MANAGER system contract.
- [VitalikButerin: keyed nonces are not just stronger in protocol support for privacy solutions, but potentially a first foray into a new state scaling strategy: new types of storage optimized for categories of use cases we care about](https://x.com/VitalikButerin/status/2051675198068330996), 21:47.
- [soispoke: privacy protocols will become first class citizens on Ethereum, with a Dune dashboard of nullifier state growth for planning](https://x.com/soispoke/status/2051565770505674819), 14:32; [nero_eth: privacy and 2D nonces](https://x.com/nero_eth/status/2051675750822990286), 21:49; [lightclients: privacy is good](https://x.com/lightclients/status/2051681736187412680), 22:13.

**Why it matters**
- For privacy: EIP-8250 lets privacy protocols that share one sender process transactions concurrently at the protocol level, without relayer queues.
- For state: nonces and nullifiers are small, append only data; storing them in a dedicated system contract could let them grow more cheaply than general storage, which is the per category state scaling idea Vitalik describes.

### 2. Native proof verification and the reorg window
**What happened**
- [ethresear.ch: Native proof verification](https://ethresear.ch/t/native-proof-verification/24798), 21:27: generalizes EIP-8025 so CL proof verification is program agnostic, and exposes it to contracts through a proof carrying transaction type and three opcodes (PROGRAMHASH, PUBVALUESHASH, PROOFCOUNT), so zkVM fixes ship with client releases instead of per project governance upgrades; [donnoh_eth's intro](https://x.com/donnoh_eth/status/2051672074653974639), 21:35.
- [Add EIP: Execution-Layer Reorg State Retention Window](https://github.com/ethereum/EIPs/pull/11601) (nerolation), submitted: EL clients keep state for at least 262,144 blocks (about 36.4 days) so they can process any reorg locally without resyncing, covering leak scenarios with up to about 79% of stake offline.

**Why it matters**
- For users: L2 bridge verifier contracts are a major risk; sharing L1 verification shrinks the bug surface of each project's own verifier, and the reorg window lets nodes recover on their own in extreme cases.
