## Key topics

### 1. EIP-8037/8038: the 8 invariants that will break
**What happened**
- [EF Blog: EIP-8037/EIP-8038 Glamsterdam](https://blog.ethereum.org/en/2026/11/06/glamsterdam-8037-8038), published under Marius van der Wijden's name. During Glamsterdam testing, ChainSecurity found that invariants some projects rely on will be broken by EIP-8037 (higher state creation cost) and EIP-8038 (repriced state access), because both change how certain operations and state are charged. ACD has therefore paused the hard fork process and will not fork Hoodi until this is resolved. Hegotá work is unaffected and continues at full speed in parallel.
- The EF is working with two audit firms, ChainSecurity and Dedaub, and running internal audits, but cannot cover every project, so it issued a call to action: the [glamsterdam-gas-invariants self-check repository](https://github.com/ethereum/glamsterdam-gas-invariants) explains each invariant with examples and prompts you can use directly to check a project. If you are affected, contact glamsterdam@ethereum.org.
- The repository README (last changed 11-05 17:44) gives new prices measured against the Amsterdam spec: a cold write to a new storage slot rises from 22,100 to 110,020 (including 97,920 state gas); creating an account by sending value to an empty address costs 183,600 state gas; CREATE/CREATE2 to an empty address costs 195,600; code deposit rises from 200 to 1,530 per byte; and **one EIP-7702 authorization for an empty authority rises from 25,000 to 235,606**. A reservoir separate from `gasleft()` exists only when the transaction gas limit is above 2^24.
- The 8 invariants fall into two groups: price invariants (P, broken by any repricing) and accounting invariants (A, from EIP-8037's new way of tracking gas). The one that touches accounts directly is INV-8: when a delegation is rolled back for lack of gas, the transaction is still included and the signed 7702 delegation can be reused by anyone. The advice is to bind a wallet's `setup`/`initialize` to the signature and to check the account code after the transaction.
- [Marius: please check that your contracts still work after Glamsterdam](https://x.com/vdWijden/status/2118650300706046299), 17:22; [ralexstokes: all Ethereum developers, please take a look](https://x.com/ralexstokes/status/2118665659043455460), 18:23.

**Why it matters**
- This is a head-on conflict between "raising the gas limit requires repricing" and "do not break immutable contracts". Risky patterns listed in the README: gas numbers hard-coded in contracts, settings, signed messages, bots or relayers; charging or refunding by the difference between two `gasleft()` readings; guessing "it ran out of gas" from empty revert data or remaining gas; relying on the 2,300 stipend of `transfer`/`send`.
- For accounts and transactions: sending tokens to a new address for the first time, creating accounts and first-time 7702 authorizations all get noticeably more expensive, so wallet and relayer gas estimates need to be redone under the new rules. Users do not need to do anything yet; contract teams should run the self-check repository now.

**What to watch**
- When the audit reports are published, and whether the next ACD discusses changing the specs.

### 2. A privacy pool on Frame Transaction: what works and what is still missing
**What happened**
- [ethresear.ch: a privacy pool on frame transactions](https://ethresear.ch/t/a-privacy-pool-on-frame-transactions-what-works-and-the-case-that-does-not-yet/26223), posted at 20:00 by Daniil Ankushin of Nethermind, with measurements by Manuel Arto. On frame transactions the privacy pool pays its own gas, so private withdrawals need no relayer. They ran a real BN254 Groth16 pool (soispoke's minimal-shielded-pool) on current Nethermind master: one withdrawal costs 679,322 gas. During a withdrawal the pool contract is the sender, its VERIFY code checks the zk proof and approves execution and payment, and the user needs no funded account and does not appear in the transaction. With EIP-8250 keyed nonces, several withdrawals can run concurrently from the same pool address.
- Two things do not work yet: proof verification exceeds the validation gas limit in the spec, and the pool cannot yet pay for calls made from the user's own address.
- [EIPs PR #12632: EIP-8288 places dependent frames around protocol verification frames](https://github.com/ethereum/EIPs/pull/12632), opened at 12:52, adjusting where each kind of verification frame can sit in the public mempool.

**Why it matters**
- Relayers are today's biggest point of centralization and metadata leakage for privacy pools. Letting the pool pay its own gas through native AA removes the relayer at the protocol level. How high MAX_VERIFY_GAS is set decides whether this can run in the public mempool at all.

**What to watch**
- Whether the validation gas limit is raised, and the DoS risk assessment that comes with it.

### 3. Transaction assertions and the PBT state migration
**What happened**
- [EF: if assertions ship with Hegotá, users can sign with more confidence](https://x.com/ethereumfndn/status/2118479704412045627), 06:04. User interviews keep coming back to people not being sure what they are signing. With assertions, the wallet shows the exact effect, and the transaction either does what was expected or reverts in full. Background: [EF Blog: how native transaction assertions enforce a transaction's final outcome](https://blog.ethereum.org/en/2026/10/05/transaction-assertions) (2026-10-05).
- [EF: I* plans to rebuild the state structure without downtime](https://x.com/ethereumfndn/status/2118510132854460793), 08:05. A Partitioned Binary Tree (PBT) shrinks state proofs so that wallets can verify instead of trusting, and paves the way for state expiry. [EIPs PR #12633: EIP-8347 specifies readiness at activation and late migration](https://github.com/ethereum/EIPs/pull/12633), opened at 16:58, covering nodes whose PBT is not ready when the activation block arrives (they should return SYNCING rather than mark the block invalid).

**Why it matters**
- Assertions are user protection at the transaction layer, directly related to the Binance question of what a signing service is able to authorize. PBT decides whether light wallets can verify account state themselves.
