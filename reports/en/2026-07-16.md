## Key topics

### 1. ACDE #241 and the Glamsterdam timeline
**What happened**
- Per Ethereal news #31, ACDE #241 (21:00): glamsterdam-devnet-7 is open to app developers with a faucet and RPC and a 300M gas limit; devnet-8 is likely the last devnet before public testnets upgrade; mainnet is at least 3 months away (30-day security review, 2 weeks between testnets, 30 days' notice for the mainnet upgrade); the upgrade mascot goes to a runoff between flamingo and polar bear. Hegotá's headliner is FOCIL (EIP-7805), native AA (EIP-8141 frame transactions) is CFI, EIP-8268 (storage roots in BALs) was proposed for inclusion, and the deadline for non-headliner proposals is August 6.
- [nixorokish: app developers can test Glamsterdam on devnet-7 before Sepolia/Hoodi](https://x.com/nixorokish/status/2077762286132109417), 21:28.
- [EIP-8081: list EIP-7862 delayed state root as PFI](https://github.com/ethereum/EIPs/pull/11934) (nixorokish), submitted and merged; [EIP-8081: propose EIP-8298 for inclusion](https://github.com/ethereum/EIPs/pull/11881), merged; [EIP-8081: add EIP-8304 as PFI](https://github.com/ethereum/EIPs/pull/11933) (zsfelfoldi), submitted.
- [New EIP: Partial Execution Payload Commitments](https://github.com/ethereum/EIPs/pull/11936) (nerolation), submitted; per Ethereal news #31 it is numbered EIP-8341. It is an alternative to EIP-7862 that avoids a delayed state root on the execution layer while still giving builders and provers more time.

**Why it matters**
- For app teams: 3 months is the shortest path, and devnet-7 is the window to test the new gas rules before public testnets.

### 2. EIP-8141 spec clarifications
**What happened**
- svlachakis submitted several clarifications at once: [pin the SECP256K1 signature encoding (recovery id and low-s)](https://github.com/ethereum/EIPs/pull/11937), since `validate_signature` passed signatures straight into `ecrecover` without defining `v` or requiring a canonical `s`; [note that execution approval authorizes all subsequent sender frames](https://github.com/ethereum/EIPs/pull/11939), because `sender_approved` is a transaction-scoped flag, not scoped to a frame or target; [specify EIP-3529 storage refund accounting for frames](https://github.com/ethereum/EIPs/pull/11940); [apply the EIP-7623 calldata floor to frame and signature data](https://github.com/ethereum/EIPs/pull/11941), since the transaction's gas was never floored; [define the Receipts message encoding for frame transaction receipts](https://github.com/ethereum/EIPs/pull/11942); and [the stack operand order for FRAMEDATALOAD/FRAMEDATACOPY](https://github.com/ethereum/EIPs/pull/11938).
- [Bounding the signatures list with MAX_SIGNATURES](https://github.com/ethereum/EIPs/pull/11935) was also proposed: `signatures` is the only variable-length list in the frame transaction family without an explicit bound, limited only implicitly by `tx_gas_limit`, which allows thousands of entries.

**Why it matters**
- For wallets and clients: signature malleability, approval scope and the calldata floor all decide whether different clients validate and charge a transaction consistently, and "after approval every sender frame runs as `tx.sender`" is a security semantic wallets must know when building multi-frame transactions.

### 3. 8130 metadata and confirmation
**What happened**
- [ERC-8340: Transaction Metadata Encoding](https://github.com/ethereum/ERCs/pull/1883) (chunter-cb), submitted, with [forum discussion](https://ethereum-magicians.org/t/erc-8340-transaction-metadata-encoding/29022) at 06:08. EIP-8130's AA transaction has an optional opaque `metadata` field; this ERC defines it as a deterministic CBOR value (memo, commitment digest, a map of reserved keys, or an array of these), with keys compatible with ERC-8021 schema 2. Any value can be replaced by a salted commitment for selective disclosure, and the ERC specifies an offchain proof package and ERC-5792 integration.
- Ethlabs announced that [Francesco is joining](https://x.com/ethlabs_org/status/2077739868025762252), 19:59; per Ethereal news #31 he is moving from the EF. [fradamt: the goal is fast finality asap, but fast confirmation is already here, giving a very strong confirmation in seconds, 98% faster than finality, now on Glamsterdam devnets](https://x.com/fradamt/status/2077760553062170768), 21:21. [Ben Edgington: confirmation is for peacetime, finality is for wartime](https://x.com/benjaminion_xyz/status/2077764224617447592), 21:36.

**Why it matters**
- For payments and compliance: metadata lets invoice numbers, attribution and commitments travel with a transaction without publishing plaintext, which also serves privacy needs.
