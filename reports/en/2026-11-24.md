## Key topics

### 1. Native AA and Frame transactions: EIP-8430 merged, EIP-8141 tightens signature data reads
**What happened**
- [EIP-8430 AA Transaction Type was merged as a draft](https://github.com/ethereum/EIPs/pull/12385) on 2026-11-23 at 14:56 (chunter-cb). The PR lists phased call batching (calls can carry native ETH); gas sponsorship with bound and open payer modes; 2D nonces (key 0 is the account nonce) and a nonce-free mode; and in-band EIP-7702-style code delegation (account_changes type 0x01). An authenticator selector, an actor-resolution hook and reserved account-change types let other account models plug in without a new transaction type; EIP-8130 (Keystore Accounts) specifies one such integration in PR #12386. [Discussion thread](https://ethereum-magicians.org/t/eip-8430-aa-transaction-type-split-out-from-8130/29810).
- [PR #12708: EIP-8141 lets only VERIFY frames read signature bytes outside the signature hash](https://github.com/ethereum/EIPs/pull/12708), 2026-11-23 21:00 (soispoke). For an ARBITRARY entry with an empty msg, the signature hash covers only its length, so anyone relaying the transaction can change those bytes, and today code in any frame can copy them. With the change, SIGDATACOPY on such an entry halts outside a VERIFY frame, so any custom witness check over the signature hash has to run in a VERIFY frame.
- [PR #12506: EIP-8141 sets code from the default code in SENDER mode](https://github.com/ethereum/EIPs/pull/12506), updated 2026-11-23 18:14 (AnkushinDaniil). Following lightclient's suggestion, the default code in SENDER mode reads frame.data[0] as a selector, where 0x01 means set code, and runs EIP-8298's SETCODEFROM on tx.sender. No new flag is added, and EIP-8298 joins the requirements.
- [PR #12672: EIP-8504 supports leanSPHINCS signatures through dependency frames](https://github.com/ethereum/EIPs/pull/12672), updated 2026-11-23 23:03 (ilitteri). A dependency verification frame runs no code and only declares (scheme, data_hash, verification_key_hash) triples, with only leanSPHINCS enabled for now. Signature witnesses travel separately from transactions through the EIP-8288 aggregation interface, and the block header commits to the signatures carried.
- [PR #12663 (FOCIL omission witnesses for Frame transactions) was closed](https://github.com/ethereum/EIPs/pull/12663) on 2026-11-24 at 01:37 without being merged.
- [ACDT #104 meeting summary](https://ethereum-magicians.org/t/all-core-devs-testing-acdt-104-november-23-2026/30411/3): forward compatibility between the Frame spec and EIP-8288 sparked debate over whether LeanPCS and leanSPHINCS should come in through a proof frame or through additions to the signature list, touching on aggregation, malleability and L2 integration. The call agreed to continue async in the pq-el and 8141 channels. (The summary was generated automatically by the meeting tool.)

**Why it matters**
- EIP-8430 offers a native AA path that existing EOAs can use without waiting for Keystore accounts. Batching, sponsorship and parallel nonces all move into the protocol, so wallets no longer need a 4337 bundler and EntryPoint to do them. It runs in parallel with EIP-8141 Frame transactions as a second design, and which one lands in Hegotá is still open.
- PR #12708 closes a class of malleability risk: bytes not covered by the signature hash can be changed by a relayer, and if execution frames can read them, a third party could influence contract behavior. Developers writing Frame account validation logic should keep those checks inside VERIFY frames.
- EIP-8504 and the ACDT discussion show Frame transactions being treated as the main entry point for post-quantum signatures at the account layer, with signature data that can be aggregated at the block level.

**What to watch**
- Whether the next ACD settles how Frame transactions support leanSPHINCS (proof frame or signature list), and whether it goes into Bogota Devnet 3.
- How EIP-8430 and EIP-8141 are weighed in the Hegotá scoping discussion.

### 2. EIP-7702 authorization freshness and delegation risk in agent accounts
**What happened**
- [EIP-8477 Recent Block Bound Delegation Authorizations was merged as a draft](https://github.com/ethereum/EIPs/pull/12601) on 2026-11-23 at 14:59 (dangerousfood). The motivation: unused EIP-7702 authorizations have no protocol-enforced freshness bound and stay usable whenever the account nonce matches. The proposal extends the type 0x04 authorization format so it signs an execution block number and header hash, and allows it only while that block is one of the inclusion block's 256 preceding ancestors. It keeps the 0x05 signing prefix, rejects legacy unanchored authorizations after activation, leaves authorization-list processing unchanged and does not expire installed delegations. [Discussion thread](https://ethereum-magicians.org/t/eip-8477-recent-block-bound-delegation-authorizations/30269).
- [Policy-Enforced Agent Accounts shipped Registry v2](https://ethereum-magicians.org/t/draft-erc-policy-enforced-agent-accounts/30467/10) on 2026-11-24 at 03:21 (palisec-dev). Following review, every policy the publisher posts now goes through setPending at least the account's minDelay ahead, and only the account itself can activate immediately. The registry is deployed on Robinhood Chain (4663) with no owner and no upgrade path, and client library 0.2.0 is on npm. Earlier, [palisec-dev replied to Secrypta](https://ethereum-magicians.org/t/draft-erc-policy-enforced-agent-accounts/30467/7) (2026-11-23 14:39) agreeing that Security Considerations will state that a commitment only covers actions needing the policy signer, and that readers must separately check allowances and permits, operator approvals, installed modules and executors, guards and hooks, fallback handlers, and the ERC-7702 delegation target. [Secrypta suggested](https://ethereum-magicians.org/t/draft-erc-policy-enforced-agent-accounts/30467/8) (2026-11-23 16:39) making a snapshot of that fund-moving surface a separate companion ERC, since a snapshot is only accurate at the block it is taken.
- [ERC-8516 Sovereign ERC-20 Receive Protection](https://ethereum-magicians.org/t/erc-8516-sovereign-erc-20-receive-protection/30485), 2026-11-23 22:55 (radek): an opt-in ERC-20 extension that lets both EOAs and smart accounts gate incoming transfers and mints (allowlists, denylists, one-off offchain signatures or external policy contracts), aimed at address poisoning and spam transfers. [ERCs PR #2213](https://github.com/ethereum/ERCs/pull/2213).

**Why it matters**
- A 7702 authorization is a signature that says "set my account's code to this contract". With no expiry, an authorization signed long ago and never used can still be submitted. EIP-8477 makes authorizations short-lived. For wallets, that means an authorization has to land onchain within about 256 blocks of signing (roughly 51 minutes at 12-second blocks), so presigning offline and holding authorizations for a long time stops working.
- The agent account debate keeps arriving at the same place: what can actually move funds is usually permissions granted earlier and the current 7702 delegation target, not the policy itself.

**What to watch**
- Whether EIP-8477 gets proposed for a fork, and how wallets and sponsored-transaction services handle re-signing after an authorization expires.
- A draft of the companion "fund-moving surface snapshot" ERC for Policy-Enforced Agent Accounts.

### 3. Gas repricing and post-quantum priorities: ACDT #104 and PQAI #0
**What happened**
- [ACDT #104](https://ethereum-magicians.org/t/all-core-devs-testing-acdt-104-november-23-2026/30411) met on 2026-11-23, opening with team feedback on Glamsterdam's EIP-8037/EIP-8038. Per [the meeting summary](https://ethereum-magicians.org/t/all-core-devs-testing-acdt-104-november-23-2026/30411/3), Rahul (EF) collected feedback from teams: Uniswap, Snowbridge, CoW Swap, Safe and others are concerned about the try-catch pattern breaking and about the gasleft invariant, and most high and medium severity issues are expected to be addressed by mid-January. Toni Wahrstätter walked through a decision tree of possible EIP-8037 spec changes, and Maria Silva explained that dropping the reservoir mechanism would require a much higher transaction limit and would hurt parallelization. Most leaned toward not changing the spec for now, with the final decision at the next ACD. Opinions on whether to run Bogota Devnet 3 were split, and that was pushed to next week.
- [EIP-8487 Separate execution credits and billing credits](https://github.com/ethereum/EIPs/pull/12637), updated 2026-11-23 14:59 (Giulio2002): two counters start from the same tx.gasLimit. Credits use the legacy schedule and govern EVM-visible execution allowances, billing uses the new schedule and sets the fee, and running out of billing aborts the whole transaction uncatchably. It is one way to reprice without breaking contracts' gas assumptions.
- [New draft: Bounded Storage Credit and Debit](https://github.com/ethereum/EIPs/pull/12707), 2026-11-23 19:18 (cskiraly), a successor to the stagnant EIP-7519. SCREDIT and SDEBIT add to or subtract from a storage slot only if its value stays within lower and upper bounds, charged like SSTORE; the upper bound serves layouts like USDC's, which keeps a blacklist flag in the top bit of each balance word. [Discussion thread](https://ethereum-magicians.org/t/add-eip-bounded-storage-credit-and-debit/30477).
- [The EF blog's PQAI #0](https://blog.ethereum.org/2026/11/23/pqai-0), 2026-11-23: after more than a year of evaluating candidate signature schemes, the EF is advocating hash-based cryptography to replace elliptic curves. The three parts are consensus (validators sign with hash-based keys), user accounts (wallets give users a way to move to hash-based signatures) and data (blobs switch to hash-based commitments). The post notes Justin Drake proposed December 2028 as a target at Devcon, with 2029 still the EF's internal deadline and a review in January; Ethlabs pulled its own Quick Slots proposal out of Hegotá to free up engineering time, and the EF doubled its protocol security team. The remaining ACD calls this year will discuss what else to drop from the fork. [Shared by @ethereumfndn](https://x.com/ethereumfndn/status/2125011648675029353) (2026-11-24 06:40).

**Why it matters**
- EIP-8037/8038 are already on testnets and change how some operations and state are charged. Contracts that rely on gasleft or on try-catch keeping gas back (routers, bridges, multisigs) should check themselves before mainnet activation, and ACDT also encouraged teams to follow protocol changes on Forkcast.
- PQAI #0 says plainly that "features people have spent years on will have to wait", which points to a Hegotá scope that shrinks toward post-quantum work. Wallets, multisigs and staking pools all need to prepare for a signature migration, and bigger signatures will affect node hardware requirements.

**What to watch**
- The next ACD's final call on whether to change the EIP-8037 spec.
- The January PQ timeline review and which features are moved out of Hegotá.
