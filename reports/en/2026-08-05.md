## Highlights
1. **Zero-knowledge spending policies**: ERC-8366 lets a contract holding a user's funds release them only when a zero-knowledge proof satisfies a registered policy.
2. **EIP-8141**: PR 12109 statically disallows approval scope on any frame of an atomic batch, avoiding in-batch `APPROVE_PAYMENT` divergence.
3. **FOCIL**: EIP-8369 defines two VOPS profiles, the second adding bounded validation replay for eligible frame transactions.
4. **Issuance**: the Hegotá proposal deadline is August 6, selection runs to November 8, and going live is likely around Q2 2027.

## Key topics

### 1. Spending policies and agent mandates on the account side
**What happened**
- [Magicians: ERC-8366 zero-knowledge spending policies](https://ethereum-magicians.org/t/erc-8366-zero-knowledge-spending-policies/29281), 12:37 (junbeomlee), with [ERC PR 1929](https://github.com/ethereum/ERCs/pull/1929). It standardizes a composable function set that any contract holding a user's funds (a dedicated escrow, a smart wallet, an ERC-4337 account or an EIP-7702-delegated EOA) can implement to release those funds only against a zero-knowledge proof that the payment satisfies a spending policy the owner registered in advance.
- [Magicians: ERC-8370 inheritable agent mandates](https://ethereum-magicians.org/t/erc-8370-inheritable-agent-mandates/29275), 04:39, noting that AI agents are starting to hold money onchain and spawn copies of themselves, while almost every guardrail (signing-time policy engines, session keys, per-wallet caps) is attached to a single account; [ERC PR 1930](https://github.com/ethereum/ERCs/pull/1930) was submitted the same day.
- [Magicians: ERC-8380 unclonable agent execution credentials](https://ethereum-magicians.org/t/erc-8380-unclonable-agent-execution-credentials/29274), 04:38.

**Why it matters**
- Smart accounts and 7702 EOAs can plug into the same policy interface, so wallets can restrict how funds are used without revealing the policy details, which ties directly into account privacy.

### 2. Refining EIP-8141 and FOCIL
**What happened**
- [EIP-8141: statically disallow approval scope on atomic-batch frames](https://github.com/ethereum/EIPs/pull/12109) (Marchhill), submitted. It statically disallows approval scope on any frame of an atomic batch, including its terminating frame, closing the in-batch `APPROVE_PAYMENT` divergence before execution with no rollback of the nonce, `max_cost` or `sender_approved`; because `APPROVE` requires the scope in `frame.flags`, the check is static, and the refund goes to the final `payer`.
- [New EIP: VOPS profiles for FOCIL eligibility](https://github.com/ethereum/EIPs/pull/12110) (soispoke), submitted, now EIP-8369. Profile 1 keeps the existing end-of-payload check for regular non-blob transactions, and Profile 2 adds bounded validation replay for eligible frame transactions; the PR says it supersedes the previous day's 12086.

**Why it matters**
- For wallets and builders: a batch can no longer smuggle in a payment approval, so the paying party is known before execution, which lets the mempool and FOCIL handle frame transactions safely.

**Why it matters**
- The debate moved from the issuance numbers to the process itself: the PFI bar is low, and being proposed is not the same as being included.
