## Key topics

### 1. Gas dimensions and validation rules in EIP-8141
**What happened**
- [EIP-8141: add an explicit second dimension for state gas to frames](https://github.com/ethereum/EIPs/pull/12062) (lightclient), submitted: a frame's `gas_limit` splits into `execution_gas_limit` and `state_gas_limit`; execution gas stays (generally) a call-frame-level concept while state gas is a frame-level concept, to clear up the remaining edge cases between frames and EIP-2780, 7623, 7708, 7825 and 8037.
- [EIP-8141: ban SLOTNUM during validation-prefix execution](https://github.com/ethereum/EIPs/pull/12066) (AnkushinDaniil), submitted: the validation prefix already bans opcodes whose value changes between admission and inclusion, such as `TIMESTAMP`, `NUMBER`, `PREVRANDAO`, `BASEFEE` and `BLOBBASEFEE`, since otherwise a transaction could pass simulation at admission and revert on inclusion; EIP-7843's `SLOTNUM` (`0x4B`) has the same property.
- [EIP-8141: note that a frame receipt carries no transaction-level status](https://github.com/ethereum/EIPs/pull/12061) (AnkushinDaniil), submitted: `ReceiptPayload` has no transaction-level status field, but JSON-RPC receipts have `status`; on a Nethermind/ethrex devnet, the same transaction with a reverting SENDER frame was reported as `0x1` by one client and `0x0` by the other, while all consensus fields matched.
- [EIP-8250: pin NONCE_MANAGER to 0x…8250](https://github.com/ethereum/EIPs/pull/12067) and [EIP-8272: pin RECENT_ROOT_ADDRESS to 0x…8272](https://github.com/ethereum/EIPs/pull/12068) (AnkushinDaniil), submitted; both known implementations independently chose the address equal to the EIP number, matching 8141's `EXPIRY_VERIFIER = 0x…8141` convention.

**Why it matters**
- For wallets and gas estimation: with state gas metered separately, wallets need to estimate execution and state creation separately for each frame. For wallets and explorers: until the meaning of receipt `status` is settled, judging frame transaction success through JSON-RPC can go wrong.
