## Key topics

### 1. How Frame transactions express signatures: PROOF frames or the signature list
**What happened**
- [PR #12714: add a PROOF frame mode to EIP-8141](https://github.com/ethereum/EIPs/pull/12714), opened 2026-11-25 02:59 (lightclient, still open). The author says the team has gone back and forth on whether signature_list is sufficient and future compatible, and he now leans toward a dedicated frame mode for cryptographic claims, borrowing the core idea of EIP-8288. His reasons: other EVM chains cannot easily extend the signature list, a frame mode is more permissionless, and it removes the ARBITRARY signature type from the original design. The PR adds leanSPHINCS as a protocol verifier because the scheme should be finalized in time for Hegotá. Named verifier precompiles can be PROOF frame targets directly, consuming (key, msg, proof), and any contract that implements the same interface can become a verifier. The canonical paymaster example now reads a proof frame (new opcode PROOFPARAM) instead of calling ecrecover itself, since the protocol verifies every claim before any other frame runs.
- [PR #12710: declare EIP-8288 dependencies in the signature list](https://github.com/ethereum/EIPs/pull/12710), opened 2026-11-24 17:50 (soispoke). Instead of a frame that runs no code, a dependency becomes an entry in EIP-8141's signatures list: [LEANSPHINCS_SCHEME, public key, msg, empty]. An empty msg already stands for the transaction's signature hash. The triple, the recursive proof, the wrappers, FOCIL and the price of 33,000 gas per signature stay the same, and accounts read the entry with SIGPARAM. This points in the opposite direction from #12714.
- [PR #12549 merged](https://github.com/ethereum/EIPs/pull/12549), 2026-11-24 20:52 (nerolation): the recursive STARK in EIP-8288 (In-mempool signature and proof aggregation) moves out of the block header into a separate ExecutionPayload field, recursiveStark. The header keeps two 32-byte fields, recursive_stark_hash and block_deps_hash, and a new Engine API section is added. Smaller headers help skeleton sync and let nodes fetch finalized blocks without downloading the STARKs.
- Networking split: [PR #12712](https://github.com/ethereum/EIPs/pull/12712) narrows EIP-8437 (eth/75) to direct witness propagation, and aggregate relay moves to a new draft, [eth/76 Aggregated Proof Propagation (PR #12713)](https://github.com/ethereum/EIPs/pull/12713). Both were opened 2026-11-25 02:43 (Marchhill), with a [discussion thread](https://ethereum-magicians.org/t/eip-eth-76-proof-wrapper-aggregation/30502). The goal is to let Frame transactions with dependencies propagate before mempool aggregation is deployed.
- [Project Eleven says the Daisugi devnet now combines leanSPHINCS signatures, EIP-8141 Frame transactions and EIP-8288 signature aggregation](https://x.com/projecteleven/status/2125302953594802575), 2026-11-25 01:58, and that you can send a post-quantum Ethereum transaction with its open source wallet NiceTry.

**Why it matters**
- This is a key design fork at the account layer. PROOF frames open up "who verifies the signature" to any contract verifier, so L2s and other EVM chains can add their own schemes. The signature list approach is a smaller change, but new schemes would have to be added by other EIPs. Wallet and account contract developers should watch which one wins, because validation logic would read signatures differently (PROOFPARAM versus SIGPARAM).
- If #12714 is adopted, Frame transactions would launch with a post-quantum signature verifier, so user accounts could migrate to hash-based signatures through Frame transactions rather than a separate transaction type.

**What to watch**
- [PQTS Breakout #19](https://github.com/ethereum/pm/issues/2312) (post-quantum transaction signatures) tonight at 22:00. Ahead of the call, johba37 posted data on leanSPHINCS lifetime parameters: on a 240 MHz ESP32, eight signatures averaged 15.2 seconds at 2^24 and 28.5 seconds at 2^30, and generating a key took about 30 seconds. That matters for whether hardware wallets can use it.
- Whether #12714 or #12710 gets merged, and whether EIP-8141 adds a clause letting other EIPs add signature schemes.

### 2. Post-quantum roadmap: Keccak-256 as the single hash, pacing for PQ consensus and PQ FOCIL
**What happened**
- [The EF blog's PQAI #1](https://blog.ethereum.org/2026/11/24/pqai-1), 2026-11-24 (Kev Wedderburn), recommends Keccak-256 as the hash for Ethereum's hash-based cryptography, along with a family of primitives derived from Keccak-f[1600]: Keccak-256 for standard hashing, Keccak-duplex for Fiat-Shamir, and SHAKE256 for pseudorandomness and key derivation. The post says binary-field SNARKs and GKR-based provers now prove standard hashes at or well above 500K hashes per second, so performance no longer picks the winner and security does. It compared Poseidon/Poseidon2, BLAKE3, BLAKE2, SHA2-256 and Keccak-256. For clients: the execution layer needs no new hash and signature verification reuses existing Keccak-256 code; if SSZ comes to the execution layer with Frame transactions, Keccak-256 is recommended there. In the long term the consensus layer is advised to move SSZ merkleization from SHA2-256 to Keccak-256. [kevaundray's post](https://x.com/kevaundray/status/2125345585943208051) (2026-11-25 04:47), [quoted by @ethereumfndn](https://x.com/ethereumfndn/status/2125356914846445600) (2026-11-25 05:32).
- [PQ-CL Breakout #4](https://ethereum-magicians.org/t/pq-cl-breakout-4-november-24-2026/30460) took place on 2026-11-24. Per [EIPsInsight's follow-up](https://ethereum-magicians.org/t/pq-cl-breakout-4-november-24-2026/30460/4) (2026-11-25 03:08): delayed XMSS key generation caused a 55-slot reorg and clients are working on pre-generation and caching; LeanVM 0.17 replaces the sidecar with FFI and recursion is about 15% faster, with all clients needing a coordinated update; a separate aggregator role is deferred from the first PQ fork. [EIPsInsight's recap](https://x.com/EIPsInsight/status/2125286589643522513) (2026-11-25 00:53) says pq-devnet-1 will focus on aggregation and timing. The next call, [PQ-CL Breakout #5](https://ethereum-magicians.org/t/pq-cl-breakout-5-november-27-2026/30499), is on November 27.
- [FOCIL Breakout #47](https://ethereum-magicians.org/t/focil-breakout-47-november-24-2026/30420) took place on 2026-11-24. Per [EIPsInsight's follow-up](https://ethereum-magicians.org/t/focil-breakout-47-november-24-2026/30420/4): PQ signatures of 5 to 7 KB could initially support up to 16 PQ transactions per block without major networking changes, and the EIP-8288 roadmap is split into three parts. [EIPsInsight's recap](https://x.com/EIPsInsight/status/2125263748994912375) (2026-11-24 23:22) says a final decision on FOCIL's scope in Hegotá is targeted for December 10.

**Why it matters**
- For user accounts, Keccak-256 is already the hash behind Ethereum addresses and execution-layer state, so wallets, contracts and SDKs moving to hash-based signatures will not have to adopt a third general-purpose hash. That keeps audit and implementation costs down.
- PQ transactions fitting into FOCIL inclusion lists means transactions from post-quantum accounts can get censorship resistance too, though capacity starts small (up to 16 per block).

**What to watch**
- PQ-CL #5 on November 27 and progress on pq-devnet-1; whether FOCIL stays in Hegotá on December 10.

### 3. Agent account permissions and gas repricing
**What happened**
- [ERC-8511 Policy-Enforced Agent Accounts discussion](https://ethereum-magicians.org/t/erc-8511-policy-enforced-agent-accounts/30467/13): on 2026-11-24 at 19:54, Revinand pointed out that in v2 both clearing signers and declaring while policySigner is zero take effect immediately, so an account can swap its signers and lower minDelay in one transaction. [Zealynx reproduced it](https://ethereum-magicians.org/t/erc-8511-policy-enforced-agent-accounts/30467/14) (20:22). [palisec-dev released Registry v3](https://ethereum-magicians.org/t/erc-8511-policy-enforced-agent-accounts/30467/15) (21:44) on Robinhood Chain (4663), with no owner and no upgrade path. A stop the account engaged can only be lifted by the account, and a publisher's attempt reverts. The author adopted the reading that minDelay binds the publisher only and now says so in Security Considerations; readers who need a delay on the account itself should watch SignersDeclared and PolicyActivated sent by the account. The client library is now 0.3.0. [Zealynx then noted](https://ethereum-magicians.org/t/erc-8511-policy-enforced-agent-accounts/30467/16) (2026-11-25 01:09) that a leaked publisher key could queue version type(uint64).max, which would get stuck permanently if the account misses the window, and suggested setPending only allow the next version. [ERCs PR #2196](https://github.com/ethereum/ERCs/pull/2196) has been updated.
- [ethresear.ch multidimensional fee discussion](https://ethresear.ch/t/more-meters-or-more-prices-one-vs-multi-dimensional-fee-mechanisms-on-ethereum/26244/7), 2026-11-24 21:25 (M1kuW1ll): after the EIP-8037 state repricing, the same state creation activity will cost more than 5x the gas it does today, and in the EIP-7999 simulations state makes up more than 99% of the block charge because state demand is the most elastic.
- [ACDT #105 agenda posted](https://ethereum-magicians.org/t/all-core-devs-testing-acdt-105-november-30-2026/30500), 2026-11-24 23:27. The call is on November 30 at 21:00, and the first item is again the status of Glamsterdam EIP-8037/EIP-8038, plus Bogota Devnet 3.

**Why it matters**
- For accounts run by AI agents, security promises have to say exactly who they bind. If counterparties assume the account is also delayed, they will misjudge the risk, and details like this decide whether custodians or merchants can trust agent wallets.
- State creation (new accounts, new storage slots) is getting much more expensive. Apps that deploy contract accounts or create many addresses, such as deploying a smart account per user, should estimate the fee change early.

**What to watch**
- Whether ERC-8511 adds a version step limit; the final EIP-8037 decision at ACDT #105 and ACDE #250 (December 3).
