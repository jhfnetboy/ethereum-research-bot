## Highlights
1. **An expiry for 7702 authorizations**: EIP-8477 has each delegation authorization commit to a recent block number and block hash, valid only for the next 256 blocks, so authorizations cannot be stockpiled and replayed later.
2. **Frame Transaction makes room for PQ signatures**: lean SPHINCS is added, and the calldata cost of signature data is excluded from the 100k MAX_VERIFY_GAS. Otherwise a PQ signature would exceed the limit on size alone.
3. **Glamsterdam spec errata**: 7 PRs submitted at once fix the EIP-2780 delegation target warming rule, incorrect wording in EIP-8037/8038 and more, without changing any gas rules.

## Key topics

### 1. EIP-8477: 7702 delegation authorizations with freshness
**What happened**
- [EIP-8477 Recent Block Bound Delegation Authorizations discussion thread](https://ethereum-magicians.org/t/eip-8477-recent-block-bound-delegation-authorizations/30269), opened at 00:39 by dangerousfood, names the 7702 sweeps in the Binance incident as its motivation. In addition to chain ID, delegate address and nonce, every authorization also signs a recent execution block number and block header hash. When included in block N, the signed block must be one of the 256 ancestors before N with a matching hash. Exactly 256 blocks back is still valid, 257 is not, and neither the current block nor future blocks count. Freshness is checked before signature recovery, and stale or mismatched authorizations are simply skipped.

**Why it matters**
- Today a 7702 authorization can be signed in advance and included much later. EIP-8477 shrinks its validity window to about 51 minutes (256 slots of 12 seconds), so authorizations stockpiled by a compromised signing service become useless. The cost is that an authorization must be signed close to when it is used, so offline signing, hardware wallet pre-signing and sponsor-relayed flows all need to adapt.
- Read it alongside EIP-8476 (permanent delegation opt-out): one limits when an authorization can be used, the other lets an account never accept authorizations again.

**What to watch**
- Feedback on the 256-block window from wallets and 4337/7702 sponsoring services, and whether it is submitted as a formal PR.

### 2. EIP-8141 Frame Transaction: adjusting the validation budget for post-quantum signatures
**What happened**
- [EIPs PR #12616: Update EIP-8141 add lean sphincs](https://github.com/ethereum/EIPs/pull/12616), opened at 12:26 by lightclient, adds lean SPHINCS (a hash-based post-quantum signature) to the frame transaction signature schemes.
- [EIPs PR #12617: EIP-8141 leaves calldata cost out of MAX_VERIFY_GAS](https://github.com/ethereum/EIPs/pull/12617), opened at 15:59 by nerolation. Mempool rule 6 originally said "the intrinsic cost of verifying `tx.signatures`", which could be read as including the calldata cost of the signature bytes. The revision changes it to `signature_verification_cost` and states that `frame_data_cost` and `signature_data_cost` are not counted. The reasoning: MAX_VERIFY_GAS limits the validation work a node does, while calldata cost pays for bandwidth and block space. If calldata were counted, a PQ signature would exceed the 100,000 limit on size alone.
- [Frame Transaction Breakout #8 set for November 17](https://github.com/ethereum/pm/issues/2295), agenda created at 17:17 ([Magicians announcement](https://ethereum-magicians.org/t/frame-transaction-breakout-8-nov-17-2026/30274)).

**Why it matters**
- The verification frames of native AA run computation that nobody pays for, and MAX_VERIFY_GAS decides how complex an account's signature can be. These two revisions make PQ accounts workable inside frame transactions, a concrete step toward "AA as the foundation for migrating to PQ accounts".

### 3. Glamsterdam spec errata: EIP-2780, EIP-8037, EIP-8038 and others
**What happened**
- At 21:26 flcl42 submitted 7 non-author revisions at once: [EIPs PR #12622: EIP-2780 fixes the floor reference and specifies delegation target warming](https://github.com/ethereum/EIPs/pull/12622) (in Glamsterdam the floor uses EIP-7976's `floor_tokens_in_calldata`, 4 tokens per byte and 16 gas per token, plus the EIP-7981 access list data surcharge; execution-specs already follows the corrected text), [EIPs PR #12624: EIP-8037 fixes wording that contradicts the spec](https://github.com/ethereum/EIPs/pull/12624), [EIPs PR #12626: EIP-8038 scopes the ACCOUNT_WRITE rule and the worst-case client claim](https://github.com/ethereum/EIPs/pull/12626), [EIPs PR #12623: EIP-7708 fixes gas numbers and creation transaction rules](https://github.com/ethereum/EIPs/pull/12623), [EIPs PR #12625: EIP-7778 removes a contradictory restore-original refund example](https://github.com/ethereum/EIPs/pull/12625), plus one each for EIP-7928 and EIP-7843.

**Why it matters**
- EIP-2780 (resource-priced intrinsic transaction gas), EIP-8037 (higher state creation cost) and EIP-8038 (repriced state access) are the Glamsterdam changes that directly affect the cost of every transaction, and all are in Last Call. Text that disagrees with the implementation leads contract developers to estimate gas with the wrong numbers.
