## 重点话题

### 1. 交易底价与区块大小：EIP-7702 授权正式进入底价计算
**发生了什么**
- [PR #12680：EIP-8131 与 Glamsterdam 对齐](https://github.com/ethereum/EIPs/pull/12680) 2026-11-21 15:48 合并（作者 Toni Wahrstätter）。[EIP-8131](https://github.com/ethereum/EIPs/blob/master/EIPS/eip-8131.md)（Unified Transaction Content Floor）把交易里所有用户可控字节（calldata、访问列表、EIP-7702 授权、EIP-4844 blob 哈希）统一按每字节 64 gas 计入底价，此前 7702 授权元组和 blob 哈希在底价里不收费。本次更新：
  - 授权按最大合法编码 133 字节计价；PR 说明若按 108 字节，全是授权的区块可能突破上限。
  - 底价以 EIP-2780 的基础成本为基准，不再是 21,000；EIP-7981 的附加费保留在固有 gas 中。
  - 区块大小上限改用 EIP-8037 的执行维度、按 payload 字节表述。
  - 新的影响报告覆盖 90 天、全部 1.68 亿笔主网交易：相对 Glamsterdam，0.66% 的交易多付（gas 合计增加 0.09%），全部是 blob 或 type-4（EIP-7702）交易。
- [PR #12681：EIP-8279 与 Glamsterdam 对齐](https://github.com/ethereum/EIPs/pull/12681) 2026-11-21 16:01 合并。[EIP-8279](https://github.com/ethereum/EIPs/blob/master/EIPS/eip-8279.md)（Block Access List Byte Floor）在运行时计量执行写入 EIP-7928 BAL 的字节，按每字节 64 gas 并入 EIP-8131 的底价。本次更新：
  - 按 EIP-2780、EIP-8037、EIP-8038 的新成本重算执行成本表，每个授权的底价为 11,776 gas；在 EIP-7825 单笔上限下，冷 SLOAD 绕过底价可塞进 1.546 MiB。
  - 区块大小上限拆成计量 payload（不超过 gas_limit/64）和每笔交易的固定开销，委托目标的情况给出具体数字。
  - 基于 400 个追踪区块的影响报告：按 Glamsterdam 执行成本，运行时计量最多让约 3.7% 的交易变贵（gas 增加 0.83%），按今天的成本是 17%。
- 同一天 11-21 18:04，[PR #12581](https://github.com/ethereum/EIPs/pull/12581)（EIP-2780：state gas 退还记入储备池并加入 legacy share）、[PR #12582](https://github.com/ethereum/EIPs/pull/12582)（EIP-2780：call frame 的 state gas 额度）和 [PR #12588](https://github.com/ethereum/EIPs/pull/12588)（EIP-8141：把 EIP-8037 的 legacy share 作为额外执行 gas 收取）由作者关闭，未合并。#12581 的讨论里，gretzke 曾以 Uniswap v4 PositionManager 的 `notifyUnsubscribe{gas: 150,000}` 为例指出，同一调用是否耗尽 gas 取决于用户签名时的 tx.gas。

**为什么重要**
- EIP-7702 让普通账户（EOA）委托给合约代码，授权元组是账户升级的入口。EIP-8131 让授权按字节付底价，大批量授权的交易会多付一点，但 99% 以上的普通交易不受影响。
- 两项 EIP 合起来把 60M gas 区块的最坏情况大小压到约 0.89 MiB（gas_limit/64），这是继续提高 gas 上限的前提之一。
- 三个 state gas PR 关闭，说明 Glamsterdam 的 EIP-8037 计量会按现状落地：写死 gas 预算的合约和钱包要自己适配，不能指望协议层再补。

**接下来关注**
- EIP-8131 和 EIP-8279 目前都是 Draft，是否被纳入某次升级要看 ACD 讨论；[ACDE #250](https://ethereum-magicians.org/t/all-core-devs-execution-acde-250-december-3-2026/30463) 定于 12 月 3 日 21:00，议程是 Glamsterdam、Hegotá 和杂项。
- 做 7702 批量授权、赞助交易的钱包和中继：按 133 字节/授权估算底价成本。

### 2. PQ 账户签名：签名寿命、密钥轮换和“pqai”标签之争
**发生了什么**
- [EIPsInsight 在 Magicians 补充 PQTS #17 要点](https://ethereum-magicians.org/t/post-quantum-transaction-signature-pqts-breakout-17/30058/5) 2026-11-21 23:23（会议本身在 10 月 28 日，[完整笔记](https://eipsinsight.com/calls/pqts/017)）：
  - 密钥轮换：5 家大型交易所表示自动轮换密钥比较容易；按 2^24 次签名的寿命，Circle 的交易量大约每 1.5 年要轮换一次。
  - 硬件钱包：Project 11 指出签名寿命更高时 Ledger 的性能限制明显。
  - 隐私：剪枝能加快密钥生成，但约 75 次签名后有隐私上的取舍。
  - Forest-of-WOTS 签名快 30% 以上，但有 MPC 兼容和安全分析上的难题；基于 SNARK 的 proof-of-grinding 未来可能带来 10 倍提升。
- [PR #12672（leanSPHINCS 依赖 frame）](https://github.com/ethereum/EIPs/pull/12672) 2026-11-21 17:36 合入 abcoathup 建议的编辑修改；此前 11-20 已补齐依赖验证 frame 的编码、leanSPHINCS 方案定义（32 字节公钥、32 字节消息和 leansphincs_verify 接口固定，其余参数暂定）。PR 仍是草案，待分配正式编号。
- X 上的讨论：[gballet](https://x.com/gballet/status/2124054653151092846) 2026-11-21 15:17 认为“pqai”是个危险的标签，抗量子不等于抗 AI，二者可能要取舍；[donnoh](https://x.com/donnoh_eth/status/2124059038564630744) 15:35 表示赞同并在写文章。[Dankrad](https://x.com/dankrad/status/2124069866147848647) 16:18 回应：选非常保守的 PQ 方案也更可能扛住 AI 密码分析，还可以叠加，比如用 SPHINCS 的同时仍要求一个椭圆曲线签名，安全性严格提高；他 [16:43 补充](https://x.com/dankrad/status/2124076187806765076)没有方案能被证明不可破，哈希签名也依赖具体哈希函数，而加一个 EC 签名几乎没有成本。[barnabé](https://x.com/barnabemonnot/status/2124170965575971042) 22:59 表示 pqai 并不排斥双签名方案。

**为什么重要**
- 签名寿命直接决定 PQ 账户什么时候必须换密钥：寿命越短，签名越小、硬件钱包越快，但高频签名方（交易所、支付机构）要更频繁轮换。这会写进钱包和托管方的运维流程。
- “PQ 签名 + EC 签名”双签名如果成为主流做法，账户验证代码和 VERIFY 阶段的 gas 预算都要为两个签名留出空间，这与上期 MAX_VERIFY_GAS 提到 30 万的讨论直接相关。

**接下来关注**
- 默认签名寿命（2^24 或更高）是否定下来；PR #12672 何时拿到编号，以及 Iván 是否在下次 ACDE 提议纳入 Hegotá。
- 钱包团队：评估硬件设备在不同签名寿命下的签名耗时，以及自动轮换的用户体验。

### 3. Agent 账户与隐私：策略可读、关联可查
**发生了什么**
- [Draft ERC：Policy-Enforced Agent Accounts](https://ethereum-magicians.org/t/draft-erc-policy-enforced-agent-accounts/30467) 2026-11-21 23:07 由 palisec-dev 发起，对应 [ERCs PR #2196](https://github.com/ethereum/ERCs/pull/2196)。它只定义“读取和证据层”，不规定如何执行：
  - 发现接口（ERC-165）：policySigner、policyOf、pendingPolicyOf、mandateOf、isStopped，可以由账户自己提供，也可以由单例注册表为 Safe 等已有账户提供。
  - 策略承诺：策略文档 RFC 8785 规范化 JSON 的 keccak256 哈希，可附 URI 供人核对。
  - 待生效的放宽公开 effectiveAt，给监控方反应时间；拒绝原因用只增不减的 bytes32 列表；决策收据用 EIP-712 签名，绑定链、账户、目标、金额、calldata 哈希和策略哈希，合约签名者走 ERC-1271。
  - 作者称它与 ERC-7579、ERC-7780（账户内执行）、ERC-7710（带限制的委托）、ERC-8226 互补；参考注册表已部署在 Robinhood Chain 主网（4663）。
- [Zealynx 的评审](https://ethereum-magicians.org/t/draft-erc-policy-enforced-agent-accounts/30467/3) 2026-11-22 06:08 指出：activate 接受任何更高版本并立即生效，注册表只看到哈希，分不清收紧还是放宽，延迟机制形同虚设；验证收据时不检查当前策略版本和 isStopped，也不记录 decisionId，同一收据可重复使用；Safe 的 call 和 delegatecall 得到相同的 intentHash，意图里应加入 operation 或 ERC-7579 执行模式。
- [Pre-ERC：Agent Linkability Report](https://ethereum-magicians.org/t/pre-erc-agent-linkability-report/30462) 2026-11-21 15:03（[ERCs PR #2193](https://github.com/ethereum/ERCs/pull/2193)）提出一种报告格式，说明从公开链上数据能把 ERC-8004 agent 的所有者、agentWallet、收款地址关联到什么程度；每个字段要么附证据，要么注明未读取的原因。作者 11-21 读取 Robinhood Chain 身份注册表，26,235 个 agent 里有 25,620 个没有独立于所有者的 agentWallet，付款直接落到所有者地址。
- FHE 隐私争议：上期以太坊官方账号发布 Zama 客座长帖后，围绕 Zama 的讨论继续。[pcaversaccio](https://x.com/pcaversaccio/status/2124077434697846817) 2026-11-21 16:48 批评这是“依赖厂商的隐私”，代码许可不授予专利权，商业部署需要 Zama 许可；[donnoh](https://x.com/donnoh_eth/status/2124153379895267352) 21:50 认为很多情况下能用线性运算推出准确金额或很窄的范围，之后的交易还可能回溯泄露隐私。

**为什么重要**
- 越来越多资金由 agent 账户操作。策略能否被外部读取和核验，决定借贷方、钱包能否信任一个 agent 账户的限额；评审发现的问题说明“公开延迟”必须对发布者本身也生效才有意义。
- 关联报告把“隐私泄露”变成可比较的数据，钱包可以据此提示用户给 agent 配置独立收款地址或隐身地址（ERC-6538/5564）。

**接下来关注**
- PR #2196 作者如何回应 Zealynx 的问题（最小延迟、收据防重放、Safe 操作类型）。
- 用 agent 收款的开发者：至少把 agentWallet 和所有者地址分开。
